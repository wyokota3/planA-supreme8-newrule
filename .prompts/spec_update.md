# 仕様変更プロンプト

このファイルは **ChatGPT または Claude チャット** で使うプロンプトです。
既に作成済みの SPEC.md を変更する必要が生じたときに使います。

## 使い方

1. 外部チャットを新規で開く(既存セッションの汚染を避けるため)
2. 以下のプロンプトを貼り付け
3. 現在の SPEC.md の中身、TEST_STRATEGY.md の中身、変更の動機を貼り付ける
4. 変更案を段階的に練り上げる
5. 最終的に新しい SPEC.md と、変更が及ぼす影響リストを得る
6. Claude Code に戻り、変更を反映する(後述)

## なぜ別チャットでやるか

実装中の Claude Code セッションには、既存仕様前提のコンテキストが大量に乗っています。
そのセッションで仕様変更を議論すると、既存実装に引きずられて
「変更しやすい変更」しか提案されません。

外部チャットで仕様だけを見て議論することで、本来あるべき変更を考えられます。

---

既存システムの仕様変更について検討したい。あなたには **影響範囲を網羅的に考える設計レビュアー**
として振る舞ってほしい。

## 私が次に伝えること
- 現在の SPEC.md の中身
- 現在の TEST_STRATEGY.md の中身
- 変更したい動機(なぜ変更が必要になったか)
- 大まかな変更の方向性(あれば)

## あなたの役割

以下の手順で進めてください。

### 手順1: 動機の確認
変更動機を整理し、以下を明確化:
- 真の問題は何か(現象 vs 根本原因)
- この変更で本当に問題が解決するか
- 仕様変更以外の選択肢はないか(実装の工夫で済まないか)

### 手順2: 変更案の検討
2〜3個の変更案を提示。それぞれについて:
- 仕様のどこをどう変えるか(具体的に)
- メリットとデメリット
- 影響範囲の概算

### 手順3: 影響分析
私が選んだ案について、影響を網羅的に分析:
- 直接影響する機能(F-XXX)
- 間接的に影響する機能(依存関係経由)
- 影響するテスト
- 既存の設計判断との整合性(ADRと矛盾しないか)
- 未決定事項に影響を与える項目

### 手順4: 移行戦略
- 一括変更か、段階的変更か
- 既存実装の扱い(削除 / 維持 / 並行運用)
- データ移行の要否
- 後方互換性

### 手順5: 新 SPEC.md の生成
変更を反映した新しい SPEC.md を出力。
**変更点を diff 形式で別途明示すること**。

### 手順6: Claude Code への引き継ぎ指示書
Claude Code に戻ったときに何をすればよいか、具体的な指示書を生成:
- 新 SPEC.md をどこに配置するか
- 影響を受ける機能 F-XXX のリスト
- 各機能で WORKFLOW のどのステップから再実行すべきか
- 削除すべきコード・テスト
- 新規に追加すべき機能 F-XXX(あれば)
- ./decisions/ に記録すべき ADR の内容

## 議論の規約

- 「変更が小さいから影響も小さい」と決めつけない
- 既存の ADR と矛盾する変更を提案する場合、必ず ADR の見直しも併記
- 「とりあえず動く変更」ではなく「正しい変更」を優先
- 変更しなくても済む選択肢を提示し続ける
