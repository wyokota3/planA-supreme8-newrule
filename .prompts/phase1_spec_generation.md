# フェーズ1: 仕様生成プロンプト

このファイルは **ChatGPT または Claude チャット** で使うプロンプトです。
Claude Codeでは使いません。

## 使い方

1. ChatGPT または Claude のチャットで、作りたいシステムについて議論する
2. 議論が一段落したら、このファイルの「---」以下を会話に貼る
3. 段階ごとに出力をレビューし、「次へ」と指示して進める
4. 最終的に SPEC.md と TEST_STRATEGY.md が生成される
5. その2ファイルを、テンプレートをcloneした新プロジェクトの `specs/` に置く

---

これまでの議論をClaude Codeへの引き継ぎ書にまとめたい。
一発で出力せず、以下の手順で段階的に作っていく。
各段階で私のレビューを待ってから次に進むこと。

## 段階1: 議論の棚卸し

この会話を最初から読み返し、以下を網羅的に箇条書きで出力:

1. 「決まったこと」リスト
   - 各項目に、議論のどのあたりで決まったかを一言で付記
   - 「なんとなく合意した」程度のものも漏らさず含める

2. 「検討したが却下したこと」リスト
   - 却下案と、却下理由をセットで
   - 「議論には出たが選ばなかった」ものを全て

3. 「決まらなかったこと/曖昧なまま進んだこと」リスト
   - 議論で触れたが結論が出ていない論点
   - 「後で考える」と保留した項目
   - 暗黙の前提として扱われたが明文化されていない事項

4. 「議論に出ていない重要論点」リスト
   - このシステムを実装する上で本来決めるべきだが、議論で触れられなかった項目
   - 例: エラーハンドリング方針、ログ設計、テスト戦略、データ移行、運用監視など

出力したら止まる。私が「次へ」と言うまで先に進まない。

## 段階2: 構造化

段階1のリストを以下の章立てに振り分け、不足を補う。
振り分けた結果、議論で曖昧だった項目は「未決定事項」章に明示的に残すこと。勝手に埋めない。

(章立て: プロジェクト概要、アーキテクチャ、機能要件、非機能要件、設計判断、未決定事項、制約と前提、用語集 — テンプレートは specs/SPEC.template.md を参照)

出力したら止まる。次の段階に進む前に私のレビューを待つ。

## 段階2.5: 図化(直感的に理解できる絵を作る)

テキストだけでは「何を作ろうとしているか」が直感的に掴めない。段階2の構造を**Mermaid図**にする。これは後で実装の進捗マップ(dashboard.html)の素地になる。

1. **システム構成図**(`graph TD`):主要コンポーネントとデータの流れ。各ノードに、それを実装する機能ID(F-XXX)を併記する。
   - ノードには短いID(英数字)を付ける。例: `ingest`, `transform`, `store`。このIDは後で status.json と揃える。
2. **データフロー図**(`sequenceDiagram`):主要ユースケース2〜3個について、どのコンポーネントをどの順で通るか。
3. **コンポーネント責務表**:ノードID・名称・責務(3-5行)・担当機能の表。

出力形式は `specs/ARCHITECTURE.template.md` に従う。この図は最終的に `specs/ARCHITECTURE.md` として保存する。

出力したら止まる。「この図だけ見て60秒でシステムを理解できるか」を私に確認してもらってから次へ。

## 段階3: 自己レビュー

段階2の成果物について、以下の観点で自己レビューせよ:

1. 「もし私(AI)がこの文書だけを読んで実装したら、何を間違えるか」を10個以上挙げよ。
   各項目について、文書のどこを補強すれば防げるかも併記。

2. 文書内で以下の曖昧表現を全て検出せよ:
   「適切に」「いい感じに」「など」「等」「必要に応じて」「柔軟に」「分かりやすく」「使いやすく」
   検出したら、議論内容から具体化できるか、未決定事項に移すかを判断せよ。

3. 受け入れ条件のうち、テストコードに変換できない抽象的なものを全て検出し、具体化案を提示せよ。

4. 機能間の依存関係に循環や矛盾がないか検証せよ。

5. 段階1で挙げた「議論で出たが却下した案」のうち、段階2で「却下理由」が記録されていないものを検出せよ。

6. 段階2.5の図について検証せよ:(a)この図だけを見て、初見の人が60秒でシステムの全体像を理解できるか、(b)図のノード・データフローと段階2のテキストに食い違いがないか、(c)各機能(F-XXX)がどのノードに対応するか曖昧でないか。

レビュー結果を出力したら止まる。

## 段階4: SPEC.md の生成

段階3のレビュー結果を反映した最終版を、SPEC.md として一つのMarkdownファイルにまとめる。
ファイル冒頭に、未決定事項の数とリスクレベルをサマリとして記載すること。
構造は specs/SPEC.template.md に従う。各機能(F-XXX)には「対応コンポーネント」(段階2.5の図のノードID)を必ず記載する。
あわせて、段階2.5の図を反映した ARCHITECTURE.md(specs/ARCHITECTURE.template.md の構造)も確定版として出力する。

## 段階5: TEST_STRATEGY.md の生成

SPEC.md とは別に、TEST_STRATEGY.md を作成する。
構造は specs/TEST_STRATEGY.template.md に従う。
最後に「このテスト戦略の穴」を5個以上指摘し、SPEC.md の受け入れ条件のうち
この戦略では捕捉できないものを明示すること。

---

開始する。まず段階1から。
