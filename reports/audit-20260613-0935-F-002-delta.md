**実装**: `src/supreme/guard.py:173-182`

## 2. 修正による新たな穴・退行の探索

### 2-1. 上書き検査の判定経路

- **検査と書き込みのパス一貫性**: exists 検査(`sealset.py:166`)と書き込み先(`:180`)は同一の `self._body_path(sid)`(`:209-210`)から導出され、ズレはない。
- **(残存 N1・低)検証順序による tripwire の部分性**: 検査順序は (1)スキーマ `:146-148` → (2)リネージ `:153-161` → (3)上書き `:166-173`。よって**スキーマ不正またはリネージ交差のあるレコードで既存 sid を再 register した場合、ValidationError/LineageCrossError が先に出て access_log に記録されない**。封印本体は全経路で不変(どの例外でも `:180` の write に到達しない=fail-closed)であり、ADR 0010 決定1 の文言(「再 register は SealOverwriteError で拒否し、試行を記録」)は有効レコードによる試行については完全に満たす。記録の網羅性のみ部分的。テストは有効レコードのみ使用しており、この順序は契約として固定されていない(将来 (3) を先頭へ移しても既存テストは壊れない)。
- **`float(ts)` 変換不能時(残存 N2・低)**: 上書き試行で ts に float 変換不能な値(例 `"abc"`)を渡すと、記録 dict 構築時(`:168`)の `float(ts)` で ValueError → **無記録のまま例外**(SealOverwriteError でない)。封印は不変(fail-closed)で、ADR 0010 受容済み残存「記録 I/O 失敗時の無記録」(`0010:51`)と同方向・同種。なお正常登録では ts は完全未使用のため、不正 ts でも黙って成功する(契約「ts は上書き試行の記録にのみ使う」どおりで違反ではない)。
- **TOCTOU**: exists 検査と write の間に並行プロセスが書き込むレースは検出しないが、これは ADR 0010 受容済みの「並行2インスタンスの計数競合」(`0010:50`)と同じ単一書き手前提の範疇。新規の穴ではない。

### 2-2. 復元経路の変更(読み出し→構築時注入)

- 自前生成経路: 上記(3b)(3e)のとおり保証維持。`test_F002_lifetime_session.py:83-112` のプロセス跨ぎ核心テストが契約不変で残存。
- 注入経路: 旧実装は「状態ファイルが注入 guard の計数を上書き(古い state で巻き戻り=fail-open)」だったが、新実装は production 注入を構築時拒否(`sealset.py:112-116`)・dummy 注入は state 不読(`:104` の分岐構造)。**fail-open 経路が1つ消えた**(改善)。
- **(残存 N3・低)状態ファイルのキー欠落改竄**: `state.get("lifetime_session_count", 0)`(`sealset.py:366`)により、キーを削除した改竄は 0 復元=fail-open 方向。ただしこれは「count を 0 に書き戻す改竄」(初回監査④・ADR 0010 で「session_state.json の改竄(穴8 と同種)」として受容済み `0010:51`)と同一クラスであり、新規の穴ではない。型不正の改竄は初回監査時(silent or 遅延 TypeError)より改善され、構築時 GuardInputError(fail-closed)になった。

### 2-3. fail-open 方向への変化

**なし**。変化点を列挙すると: 上書き=新規拒否(closed 化)、production 注入=新規拒否(closed 化)、復元値型不正=silent→GuardInputError(closed 化)、dummy 注入時の state 適用=上書き(巻き戻りリスク)→不適用(注入側責任の明確化)。いずれも fail-closed 方向または中立。

### 2-4. オーバー実装

**なし**。今回の差分は以下に尽き、全て ADR 0010 に根拠を持つ:
- `sealset.SealOverwriteError` + 上書き検査・記録(決定1)
- `register` の keyword-only `ts`(追記)
- `SealGuard.initial_session_count` + `_is_nonneg_int` 検証(決定3+追記。`_is_nonneg_int` 自体は既存関数 `guard.py:104-106` の再利用で新設なし)
