## 検証1: 後方互換（最重要）

### 1-A. `params` がキーワード末尾で位置引数の意味を変えないか

**実現箇所**: `src/supreme/sealeval.py:376-379`
```python
def run_sealed_evaluation(seal_store, aggregate, baseline_scores, *,
                          scenario_ids, scenario_inputs, session_id,
                          issued_ts, revoked_ts, weak_items, strong_items,
                          delta_strong, config=None, params=None):
```

**判定**: 実装済（後方互換は破れていない）

**根拠**:
- `params` は `*`（bare star・378行目相当の `*,`）より後ろにある **キーワード専用引数**。位置引数は `seal_store, aggregate, baseline_scores` の 3 つのみで、`params` 追加によって位置引数の数・意味は一切変わらない。
- 既存契約（`tests/test_F013_single_session.py:22-25` の docstring が固定する前提 API）は `..., delta_strong, config=None) -> SealEvalReport`。Phase1b は `config=None` の後ろに `params=None` を追加しただけで、`config` の位置（キーワード専用領域内）も変わらない。キーワード専用領域内では引数順は呼び出しに影響しないため、`config` を渡す既存呼び出しも不変。
- 既存呼び出し側の証拠: `tests/test_F013_single_session.py:92-104` の `_run` は `scenario_ids=... delta_strong=...` まで全てキーワードで渡し **`params` を一切渡さない**。この呼び出しは `params=None` 既定で素通りする。

### 1-B. `params=None` 時に既定挙動を変えないか（core への透過）

**実現箇所**: `src/supreme/sealeval.py:437`
```python
views = core.run_supreme(snaps, params=params, config=config)
```
**実現箇所（core 側シグネチャ）**: `src/supreme/core.py:604`
```python
def run_supreme(pso_snapshots, params=None, config=None):
```

**判定**: 実装済（`params=None` は既定の未学習実走と完全同一）

**根拠**:
- `run_sealed_evaluation(params=None)` のとき `params` は `None` のまま `core.run_supreme(snaps, params=None, config=config)` に透過する。`core.run_supreme` の既定も `params=None`(`core.py:604`)であり、`docstring`(`core.py:613-615`)が「**None は現状の既定挙動（後方互換・最重要）で、既存呼び出しの結果を一切変えない**」と明記。
- F-013 機構（開封前 fail-closed・`open_eval_session`・`read_sealed_gt`・`compare_items`・`revoke_open_token`・`audit_seal_access`）は `params` の値に一切分岐しない。`sealeval.py:412-475` を通読しても `params` を参照するのは 437 行の `core.run_supreme` 呼び出し 1 箇所のみ。封印機構のどの分岐も `params` を見ていない。

### 1-C. テストによる機械検証（緑では出ない穴の確認）

**実現箇所**: `tests/test_Phase1b_sealeval_params.py:216-258`
- `test_Phase1b_params_none_equals_omitted_comparison_verdicts`(216-229): `params` キーワードを**構文上も渡さない**呼び出し(`_run_without_params_kw`・118-139行)と `params=None` の `comparison.verdicts` 完全一致を assert。
- `test_Phase1b_params_none_equals_omitted_lifetime_and_audit`(232-241): `lifetime_session_count==1` ∧ `audit_passed is True` の一致。
- `test_Phase1b_params_none_equals_omitted_session_and_token_window`(244-258): `session_id` / `token.session_id` 一致・`token.active is False`（失効済み）。
- `test_Phase1b_default_params_none_reaches_core_as_none`(353-382): `params=None` 時に `core.run_supreme` へ届く params が**全て None**であることを spy で検証（学習 params が既定経路へ漏れていないことの裏面）。

**隠れ破れの評価**: 後方互換の比較が「省略呼び出し（`params` キーワードを構文上も渡さない）」を基準にしている点が要。これは F-013 既存呼び出し（`test_F013_single_session.py:92-104`）と同一構成であり、`params=None` を既定値として注入する経路と、キーワードを一切渡さない経路の**両方**で同一結果を機械検証している。`config` を明示的に渡した場合の後方互換は専用テストでは検査されていないが、`config` の扱いは Phase1b で**一切変更されていない**（437行で `config=config` を従来どおり透過）ため、回帰リスクは構造上ない。

**判定**: **pass**

## 検証2: 封印保全が params 注入でも維持されるか

### 2-A. 単一開封・生涯1回・revoke・audit が params 注入で不変か

**実現箇所**: `src/supreme/sealeval.py:412-475`（封印機構の本体・params 非依存）
- 開封前 fail-closed: `sealeval.py:412-422`（`params` を参照せず・窓内不変条件のみで停止）
- 単一開封: `sealeval.py:425` `token = seal_store.open_eval_session(aggregate, session_id, issued_ts)`（`params` 非依存・1 回のみ）
- 単一トークン下 read: `sealeval.py:431-432`（同一 `token` で全 scenario read）
- revoke: `sealeval.py:464` `seal_store.revoke_open_token(token, revoked_ts=revoked_ts)`
- audit: `sealeval.py:467` `audit = guard.audit_seal_access(seal_store.access_log(), token)`

**判定**: 実装済（封印機構は `params` の有無で分岐しない）

**根拠**: 上記いずれも `params` を引数に取らず、`params` で挙動が変わる箇所がない。`params` が触れるのは 437 行の supreme 実走のみで、これは封印 GT の read 後・採点前のステップであり、開封トークンの発行・失効・計数には介入しない。

**テストによる機械検証**: `tests/test_Phase1b_sealeval_params.py:389-438`
- `test_Phase1b_trained_params_read_after_revoke_is_access_denied`(389-399): params 注入後の revoke 済み read が `AccessDenied`。
- `test_Phase1b_trained_params_all_reads_single_session_within_window`(402-423): 全 read が同一 `session_id="EVAL-1"` ∧ 窓 `[100.0, 300.0)` 内・拒否レコード不在。
- `test_Phase1b_trained_params_no_denied_access_records`(426-438): `session_id is None`(拒否)レコードが 0 件。
- `test_Phase1b_trained_params_run_completes_lifetime_one`(265-278) / `test_Phase1b_trained_params_audit_passed`(280-291): `lifetime_session_count==1` ∧ `audit_passed is True`。

### 2-B. 封印 GT を学習に使う経路が無いこと（fit は練習データのみ・封印は評価専用）

**コードによる確認**:
- `src/supreme/sealeval.py` 内に `fit_supreme` の**呼び出しは存在しない**（`Grep` 確認: ヒットは 399 行の docstring 言及のみ）。

**判定**: 実装済（封印 GT → 学習の経路は存在しないことをコードと Runbook の双方で確認）

## アーキテクチャ上の位置づけ

- 実現したノード: `core`（supreme統合ランナー・F-基盤-001）と `sealeval`（封印評価・F-013）の**結線**。Phase1b は新ノードを足さず、`core` の学習能力（`fit_supreme`/`run_supreme(params=)`）を `sealeval` の封印実走経路へ通す配線。
- このノードに対する充足度: 部分（封印評価が学習を反映する経路は配線完了。ただし**本番封印の実走そのものは未実施**＝研究者手動 seam が `docs/SEALED_EVAL_RUNBOOK.md:21-30` に残る。これは Phase1b のスコープ外で既知の限界）。
- 上流（入力元）の未実装: なし（`core.fit_supreme`/`run_supreme(params=)` は Phase1 で配線済み・`core.py:604,800` に実在）。
- 下流（出力先）の未実装: 本番封印実走（seam-1 実 PSO アダプタ・seam-2 baseline 実測値）は研究者手動で残る。これは ADR 0023 が build 範囲外と明示した seam であり、Phase1b の欠落ではない。
- 図とコードのズレ:
  - `specs/ARCHITECTURE.md:35,144` の `sealeval` ノード説明、`:143` の `core` ノード説明とも、Phase1b で**新たに加わった「学習 params の封印への透過」が図のノード説明に未反映**。図の `harness --> sealeval`(60行)・`sealeval` 説明文には params 配線の記載がない。
  - これは図と実コードの**機能的な矛盾ではない**（既存の結線・開封経路の記述は正しいまま）が、Phase1b で確立した「学習を封印 verdict に効かせる経路」がノード説明に載っていない。図の腐り防止として、`core` ノードまたは `sealeval` ノードの説明に「学習 params(`fit_supreme`)を封印実走へ透過（ADR 0025 P1-R4）」の追記が望ましい（軽微・done を妨げない）。
