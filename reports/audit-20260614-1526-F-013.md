### F-013-2: 項目別対比(弱5の勝敗・引き分け / 強3の δ_strong 内維持)が測定・報告され、成功目標は合否ゲートでない

**実現箇所(項目別 verdict)**: `src/supreme/sealeval.py:273-314`(`compare_items`)
```python
for item in weak_items:
    s = supreme.layer_score(item); b = baseline.layer_score(item)
    if s is None or b is None:
        verdicts[item] = "no_data"; no_data_items.append(item); continue
    verdicts[item] = _weak_verdict(s - b, delta_strong)
for item in strong_items:
    ...
    verdicts[item] = _strong_verdict(s - b, delta_strong)
```
弱: `_weak_verdict`(`sealeval.py:257-263`)= Δ>δ→win / Δ<-δ→lose / |Δ|≤δ→draw。強: `_strong_verdict`(`sealeval.py:266-270`)= 低下>δ→degraded / それ以外→maintained。ADR 0023 決定5 の文言に対応する。

**成功目標が合否ゲートでない**: `src/supreme/sealeval.py:305-314`
```python
success_goal = (
    not no_data_items
    and all(verdicts.get(it) == "win" for it in weak_items)
    and all(verdicts.get(it) == "maintained" for it in strong_items)
)
return ItemComparisonReport(weak_items, strong_items, verdicts, no_data_items, success_goal)
```
`compare_items` は**未達でも raise せず**、`success_goal` を bool フラグとして report に載せるだけ(SPEC 非機能要件「成功目標・合否ゲートでない」)。テスト `test_F013_verdict.py:332-353`(`test_F013_2_compare_items_does_not_raise_on_unmet_goal`)が「弱が全 lose の最悪構成でも例外を出さず verdict と success_goal=False を返す」を固定。**平均的ごまかしの防止**: success_goal は項目別 verdict の AND であり、弱を上げ強を下げる平均ごまかしは強の degraded で False(`test_F013_verdict.py:312-329`)。平均(overall)で合否を出す経路は無い。

**no_data≠draw(ADR 0023 決定4)**: `sealeval.py:290-292` で片側 None を no_data に分類し `no_data_items` へ。`test_F013_verdict.py:248-261` / `test_F013_all_null_layer.py:121-141` が「測れたが互角(draw)」と「測れない(no_data)」の混同を禁止。

**全null層の扱い固定(ADR 0012 着手条件2 / ADR 0023 決定4)**: `harness.overall()`(`harness.py:120-134`)が分母0層を平均から除外する挙動を `test_F013_all_null_layer.py:43-96` が固定(全null層を0算入していないことを overall==1.0 で検出)。supreme 側の全null層は `_SupremeScores.layer_score`(`sealeval.py:351-358`)が NaN/分母0 を None へ正規化 → compare_items で no_data 化。

**判定**: 実装済。項目別(弱5+強3)の win/lose/draw・maintained/degraded・no_data が決定5 に忠実に判定・報告され、成功目標は raise しないフラグとして扱われる。合否ゲート化・平均判定への退行は機構的に無い。

## オーケストレーター指摘2点の詳細判定

### 指摘1: ε 境界吸収(`_exceeds_delta` / `_EPS_ABS`/`_EPS_REL`)— 仕様意図に忠実か

**実現箇所**: `src/supreme/sealeval.py:244-254`
```python
_EPS_ABS = 1e-9
_EPS_REL = 1e-6
def _exceeds_delta(magnitude, delta_strong):
    threshold = _EPS_ABS + _EPS_REL * max(abs(magnitude), abs(delta_strong))
    return magnitude > delta_strong + threshold
```

**判定: 仕様意図に忠実(verdict 意味論を不当に変えていない)。** 根拠:
- **genuine な差は潰さない**。テスト `test_F013_2_weak_win_just_above_delta_boundary`(`test_F013_verdict.py:151-160`)= Δ=0.621-0.60=0.021。`_exceeds_delta(0.021, 0.02)` の threshold = 1e-9 + 1e-6·max(0.021,0.02) ≈ 2.2e-8。判定 `0.021 > 0.02 + 2.2e-8`(=0.0200000220) → True → win。δ を ~5e-4 超える genuine 差は ε(~2e-8)を4桁上回り win/degraded を保つ。
- **FP 誤差のみ吸収**。テスト `test_F013_2_weak_draw_boundary_exact_delta_positive`(同 126-136)= Δ=0.62-0.60。二進浮動小数で 0.020000000000000018(δ から +1.8e-17 ズレ)。`0.020000000000000018 > 0.02 + 2.2e-8`? FP 誤差 1.8e-17 は threshold 2.2e-8 を**7桁下回る** → False → draw。十進等価(Δ==δ)を draw 側へ正しく吸収。
- **TEST_STRATEGY / U5a と整合**。TEST_STRATEGY 行25「数値は許容誤差つき比較(ε は U5a 確定: |a−b|≤1e-9+1e-6·max(|a|,|b|))」。harness の連続値再現判定(`harness.py:255`)も同一式。verdict 境界に同じ ε を再利用するのは方法論的に一貫。
- ε を入れない素朴な `magnitude > delta_strong` だと、十進では境界(draw/maintained)であるべき Δ=0.62-0.60 が FP 誤差で win に倒れ、ADR 0023 決定5 の「|Δ|≤δ→draw」「低下 δ ちょうど→maintained」を**破る**。ε はむしろ決定5 の意味論を守る方向に働く。

**残存指摘 R1(文書・低リスク・コード修正不要)**: ADR 0023 決定5 の文言(`decisions/0023...md:63-65`)は「`supreme - baseline > δ_strong` → win / `|Δ| ≤ δ_strong` → draw」と十進の閉/開を述べるが、**FP 表現上の境界吸収幅(ε)を明示していない**。実装は ε を導入して「十進境界=draw/maintained」を実現しており意味論は正しいが、ADR 文面だけ読むと「なぜ verdict に ε が要るのか」が一意に追えない。ADR 0023 に1行「verdict 境界の FP 誤差は U5a/ADR 0002 の ε で draw/maintained 側へ吸収する(genuine 差は ε を遥かに超える)」を追記すれば文書とコードのズレが消える。判定への影響は無い(現状でも仕様意図に忠実)。

### 指摘2: read ts 割当(`run_sealed_evaluation`・read ごとに +1)— 衝突/窓外リスク

**実現箇所**: `src/supreme/sealeval.py:392-396`
```python
read_ts = float(issued_ts)
for sid in scenario_ids:
    sealed_gt = seal_store.read_sealed_gt(sid, token=token, ts=read_ts)
    read_ts += 1.0
```

**判定: 本テスト構成・本番想定では問題なし。ただし窓内不変条件のチェックが機構に無い(残存指摘 R2・低リスク)。**
- **衝突は起きない**。read_ts は scenario ごとに +1.0 で狭義単調増加。同一 ts の重複 read は構造的に発生しない。audit_seal_access(`guard.py:251-282`)は session_id 一致・窓内のみを要求し ts の一意性は要求しないため、+1 割当は audit に対して安全。
- **窓外化リスク(機構の穴)**: read 全件が窓内であるためには `issued_ts + (N-1)·1.0 < revoked_ts`(N=scenario 数)が必要。`is_access_allowed`/`_within_token_window` は半開区間 [issued, revoked)(`guard.py:238-248`)で、`read_ts >= revoked_ts` の read は窓外 → `read_sealed_gt` が AccessDenied(`sealset.py:328`)を送出し、`run_sealed_evaluation` は途中で例外終了する(その scenario 以降が読めない)。ドライランは N=2・窓幅200 で余裕。本番でも研究者が `revoked_ts` を十分大きく与えれば回避できる。**しかし、この前提を run_sealed_evaluation が事前に検証していない**(N が窓幅を超える構成で初めて実行時例外になる)。封印は本番1回開封のため、ここで例外終了すると貴重な開封枠を消費した上で評価が中断する痛みが大きい。
- **推奨(将来・コード修正は done の必須条件ではない)**: `run_sealed_evaluation` の冒頭で `issued_ts + max(0, len(scenario_ids)-1) < revoked_ts` を事前 assert し、満たさなければ**開封前に**明示エラーで停止する(開封枠を焼く前に止める)。あるいは read_ts を `[issued_ts, revoked_ts)` 区間で scenario 数に応じて等間隔割当にする。現状は低リスク(本番 N は少数封印=数件、窓は研究者供給で十分広く取れる)だが、fail-closed(開封前停止)に倒すと封印の生涯1回をより安全に守れる。
