0. 要旨 — 3行でいうと

  1. 音の観測から「いま何が起きているか」を8観点で答えるシステムを、ルール+ベイズフィルタに学習を足して独立実装した。旧リファレンス(同一 v1.4 で overall 0.7607)と比べ、role/relation を明確に底上げし、scene を学習で改善(CV held-out で汎化を確認)、強い項目(危険・接近・主役)を維持した。
  2. honest な層別勝敗(学習層は CV held-out で判定): 新が優 = role(+0.024)・relation(+0.091)・scene(CV 0.557>0.529)、互角 = risk/t1/mode/quality、旧が優 = t3 の1層のみ。
  3. t3 は CV で天井(0.5381)を実証= in-sample/CV でこれ以上の作り込みは過適合で逆効果。t3 の残りは「ルールの書き方」ではなく構造(上流 T2 従属・文脈ラベル)で、研究者領分(多様な実人手シナリオ + 封印実走)に委ねる(§6.3・§7)。

1. これは何をするシステムか

入力は PSO — マイクアレイ等で「分離・定位済み」の音環境データ。各時刻(0.5秒ごと)に「どこに・どんな音源があるか」(声・車・サイレン、方向と距離)が入る。L04 の仕事は、このバラバラの観測に束ねる(声と話者を同じ thread に)・ちらつかせない(時間方向に平滑化)を足して、8つの観点で解釈すること。

supreme の立場: baseline がルール+HGF だけで到達した地点を出発点に、苦手な層(scene/t3)へ学習を配備し、強い層は流用移植、mode/relation は計測で発見したルールの誤りを修正して底上げした。「静的な仮説の誤りを計測で見つけて直す」のが本プロジェクトの一貫した進め方。

2. 全体アーキテクチャ(図1)

左から右へ流れる。読み方: ①太い灰の本流(入力→各層→統合→出力)を追う。②緑の破線は品質レール(信頼度)。③紫の層は学習配備(fit_supreme)、青の層はルール。④下の点線枠はオフライン経路(増強→探索→ガード→封印評価=研究者手動)。

図1: supreme のアーキテクチャ(実装 18 ノードの要約)。 青=ルール層(強い項目は baseline から流用移植、mode/relation は計測で発見した誤りを修正)、 紫=学習層(scene/t3 を fit_supreme で配備)。 品質レール(緑)が各層へ信頼度を配る。下の点線枠はオフライン経路 — 増強→探索→ガード→封印評価。 封印評価は生涯1回開封で、研究者手動・本レポートでは未実施(数値は in-sample/CV)。

3. 作り方(開発プロセス)

役割を分けた4つの AI エージェント(仕様レビュー / テスト作成 / 実装 / 監査)をオーケストレーター(Claude)が指揮する方式で、実働4日・テスト800本(実装コードの約3倍)で構築。設計判断は ADR 29本、検証は監査レポート 26本として記録。テストを先に書いて(赤)→実装で通す(緑)→監査で仕様一致を確認、を全15機能で反復した。本プロジェクトの特徴は「静的仮説の誤りを計測で発見・修正」したこと — 開発中に構造バグ5件(scene 定数潰れ / quality vol 層取り違え / t3 規則層7語彙未配線 / mode 語彙潰し / h_q→t3 死配線)を計測で発見して直し、学習配線(fit_supreme)も当初 fit([]) で未学習だったのを CV で検出して接続した(ADR 0024〜0029)。

4. 採点方法 — 8つの「答え」と20本のテスト

システムは 0.5 秒ごとに次の8つの質問に答える。20本のテスト(計210フレーム)には人手の正解(GT)が付き、層ごとの正答率を出す。総合 = 8層の正答率の単純平均。採点は新旧で完全に同一(harness.canonical_metric_spec・micro acc・完全一致)。

6. 診断 — どこで・なぜ間違えるのか / 学習は効いたか

弱い層について「ルールが下手か、学習が足りないか、原理的に無理か」を切り分けた。結論: ①計測で見つけた構造バグは直る(role/relation/mode)、②学習は scene で汎化した(CV win 反転)、③t3 は CV 天井で in-sample/CV では詰め切り、残りは構造(上流従属・文脈ラベル)。

6.1 まず土台: 再現性とテスト

  • run_supreme_scenarios を既定・学習の両 params で各2回走行 → view がバイト一致(決定的・乱数/時刻なし)。本レポートの数値は分散ゼロ。
  • テストスイート 800 passed / 0 failed。supreme は stdlib のみ(numpy 不使用)。

6.3 学習は効いたか — CV held-out で正直に測る

学習(t3/scene)の利得は in-sample(楽観)と CV held-out(正直)を厳密に分けて測った(lineage-disjoint 5-fold・系統リークなし)。

実験(ADR 0024〜0029・各 cv-*.md):
  1. 学習配線 Phase1: 学習モジュールは当初 fit([]) で未学習だった。core.fit_supreme を run_supreme(params=) に接続し、scene CV 0.324→0.557(win 反転)。
  2. conv 較正(ADR 0027): _W_FLIP_GRID 拡張で t3 CV 0.443→0.538(overfit gap 0=汎化)。
  3. t3 CV 天井(reports/t3-grid-boundary-check.md): grid 境界探索でCV 天井 0.5381を実証。これ以上は w_conv 拡張で CV が悪化(過適合)。→ t3 改善は研究者領分。
  4. 正しく棄却した過適合: 練習増強(cv-augment=label保存で新情報ゼロ)・合成多様化(cv-author=規則層外)・mode弱会話結線(conv-A-overfit=held-out悪化)・t3 grid拡張 — いずれも CV/論理で棄却。実シナリオは v021_core 20件のみで、in-sample の作り込みは過適合に直結する。

7. 考察 — 限界の正体と、次の一手

底上げできた層(role/relation/scene)は、誤りの原因が「直せる構造」だった — role/relation は計測で見つけたルールの忠実再現漏れ、scene は学習配線の欠落。いずれも計測(混同・CV)で原因を特定して直った。

底上げできなかった層(t3)は、誤りの原因が「直せない構造」だった — T3 は上流 T2 の答えに従属し、かつ正解ラベルが「そのシナリオがどういう物語か」という文脈で決まる(baseline §6 と同じ発見)。瞬間の物理量からは原理的に届かず、in-sample で無理に合わせると過適合になる。CV 天井 0.5381 がその限界線。

次の一手は計算ではなくデータと封印: ①多様な実人手シナリオ(現状 v021_core 20件のみ)、②汚染ゼロの封印実走(研究者手動・SEALED_EVAL_RUNBOOK.md)で点推定を勝敗に確定。

8. この数字をどこまで信じてよいか

信頼度の階層(下にいくほど厳しい・正直):
① in-sample(開発セット自身の採点)= 楽観。学習列は二重に楽観。
② CV held-out(lineage-disjoint 5-fold)= 正直な汎化推定。学習層の勝敗はこの列で判定。
③ 封印 verdict(汚染ゼロの封印・生涯1回開封)= 最終確定・本レポートでは未実施(研究者手動)。
  • apples-to-apples の担保: 新旧とも harness.canonical_metric_spec で同一採点。GT は ADR 0006 の文書化マッピングで v1.4 正準化(正準化不能層はゼロ)。
  • risk_tier の分母規約: 本採点は 210 全件分母(ADR 0012)。baseline カタログは短尺 T0 をNA 除外(non-null=125)で測る規約のため、baseline カタログ値とは厳密 apples-to-apples ではない(新旧 supreme 間は同一 210 分母で厳密に揃う)。
  • 統計的有意性(U11): 20シナリオ・210フレームの点推定。少数封印の勝敗は誤差棒なしの点推定であり、有意性検定は今後の課題。

9. 今後の課題

  • 封印本番実走(最優先・研究者手動): supreme は core.run_supreme(封印PSO) で実走可能。baseline 再計測(risk_tier 210規約・quality v1.4)を取り込み、guard 発行の開封トークン下で生涯1回開封して項目別 verdict を確定。
  • t3 の研究者領分: 多様な実人手シナリオ + episode_features の分離配線(ns016 群)。
  • relation の入力契約拡張: addressing↔near_user は現状の入力では分離不能。
  • 契約フル emit(EPI-T0..T3/CTRL/NOVEL)・Delta 対応・multi-thread(ADR 0022 スコープ外)。
  • 統計的有意性(U11)の検定枠組み。

付録A: ノード図鑑 — 各部品のしくみ(触って試せます)

付録Aの各ウィジェットは Plan A 系が共有する機構(HGF / T0 / T1 / T2 / EMA / scene / t3)の体験版。supreme はこれらに学習(fit_supreme)を加えた配備版で、機構の直感は新旧で共通です。

各ノードについて「定義(何を受け取り何を返すか)/ メカニズム(どう計算するか)/ 何を判断できるか」をまとめ、主要なものにはその場で動かせるミニアプリを付けました。数式は実装(src/ns_epi/)から取った実物です。

A-1. gate — 入力の門番

定義: PSO レコード1件と現在の状態を受け取り、検証に通れば世界の状態(world_state)を更新、通らなければそのレコードを丸ごと捨てて状態を一切変えない。
メカニズム: 機械的なチェックのみ — 時刻が逆行していないか、角度が ±180° に収まるか、確率が 0〜1 か、必須フィールドがあるか。
判断できること: 「この入力は信用してよい形か」。壊れた入力が内部状態を汚すことを構造的に防ぐ(決定性の土台)。

A-2. HGF 3層カーネル — 信念の更新装置(Quality / Anomaly の心臓部)

定義: 観測値 u を1つ受け取り、信念(μ₁: いまの推定値、μ₂: その変わりやすさ、μ₃: さらにその変わりやすさ)を更新して返す。
メカニズム: 「予測→誤差→精度に応じた修正」のベイズ更新。新しい観測をどれだけ信じるかは、自分の自信(精度 π)と観測ノイズの比で自動的に決まる: μ₁ ← μ̂₁ + (π_u/π₁)·(u−μ̂₁)。パラメータ ω は「世界はどれくらい変わりやすい前提か」。
判断できること: ノイズの中から「本当の変化」だけを滑らかに追跡する。

▼ ミニアプリ: HGF が階段状の変化を追跡する様子(ω を動かしてみてください)
-4.0
灰色の点 = ノイズ混じりの観測(途中で 0→1 へ階段状に変化)。青い線 = HGF の信念 μ₁。ω を上げる(右へ)と追従は速いがノイズに振られ、下げると滑らかだが変化に遅れる — 平滑化と応答性のトレードオフを 1 パラメータで管理しています。

A-3. Quality-HGF — 「耳」は健全か

定義: 通信品質 QoS・遅延・トラック ID の安定性・観測信頼度を受け取り、健全度 h_q と下流ゲート g、レジーム(GOOD/PASS/DEGRADED/BLOCK)を返す。
メカニズム: 4要素の重み付き和をシグモイドに通して 0〜1 の健全度にし(h = σ(−2.0 + 5.0·QoS − 4.0·(遅延/200ms) − 2.5·(1−ID安定) + 1.5·信頼度))、HGF で平滑化。下流には g = 0.2 + 0.8·h を渡す(どんなに悪くても 0.2 は残す = 完全遮断しない)。
判断できること: 「いまの観測をどれだけ信じて解釈してよいか」。T2 の答えの自信(softmax の温度)はこの g で調整される。

A-4. Anomaly-HGF — 世界は異常か

定義: 観測特徴の「普段からのズレ」(z-score)を受け取り、surprise(驚き)と abnormal_prior(異常の事前確率、上限 0.8)を返す。
メカニズム: 特徴の平均・分散をオンラインで学習し(Welford 法)、ズレを HGF に通す。abnormal_prior = min(0.8, σ(μ₁ + 0.5·surprise))。
判断できること: 「これは入力の不調(Quality の担当)ではなく、世界で何かが起きた」。T1 の感度と T2 の警戒系モードを押し上げる。

A-5. Thread Manager — 音源を束ねる

定義: トラックとリンク(「この声はこの人から」)を受け取り、つながっているもの同士をグループ(thread)にまとめる。
メカニズム: リンクでつながったものを同じグループにする(Union-Find の連結成分)。それだけ — 統合・分割などの高度な操作は Phase 2。
判断できること: 「いくつの出来事が進行中か」「誰と何が一団か」。

▼ ミニアプリ: リンクを付け外しして「束ね」を見る(トラック: 声A・人B・声C・車D)

A-6. T0 + Safety Latch — 今すぐ危ないか(最後の砦)

定義: 一番気になるトラック(最接近・最速)を選び、音源の種類ごとの TTC(衝突までの時間)閾値で info/caution/danger を返す。
メカニズム: 表引き — 車・サイレンは(注意 12s, 危険 2s)、警報は(5s, 2s)、声は(2s, 1s)。サイレンは最低でも caution。Safety Latch は「TTC ≤ 0.8s またはサイレン」だけで発火し、この判定関数は品質変数を引数として受け取れない(関数の型で強制)。
判断できること: 「考えるより先に危険と言うべき状況」。入力品質がどれだけ崩れても、危険検知だけは鈍らない。

A-7. T1 — 近づいてくるか

定義: 動くものの距離の履歴から idle / approach / pass / depart を返す。
メカニズム: 距離が減り続ければ approach、最接近を過ぎれば pass、増え続ければ depart という幾何の状態機械。感度(approach と言い始める TTC 閾値 12〜15s)は Anomaly の警戒度で少し変わる。
判断できること: 「軌跡として近づいているのか、通り過ぎたのか」。

▼ ミニアプリ: 車が通過するアニメーションと T1 の答え

A-8. T2 NeuPSL-lite — どんな場面? 主役は誰?(本体の中核)

定義: 世界の状態+各信念を受け取り、mode(場面10種)・role(主役6種)・relation(関係6種)の確率分布を返す。
メカニズム: 5段の固定パイプライン — ①証拠抽出(サイレンある? 声の確率は? 人数は?)→ ②ルールで点数(logit)を加点(例: サイレン→緊急+2.5、近くで高確率の声→会話+2.5、人数3人以上→雑踏+3.0。証拠ゼロなら「静穏」既定+1.5)→ ③点数を確率に変換(softmax。入力品質が悪いほど「自信のない平らな分布」になる)→ ④前フレームと半々で混ぜる(EMA)→ ⑤複数 thread の合議。
判断できること: 場面の種別と主役。できないこと: 「さっきまで会話だったがもう終わった」のような取り下げ(§6.3 実験1)。

A-9. EMA(時間平滑化)— 「残留」を体験する

定義: 今フレームの確率分布と前フレームの結果を (1−α)·今 + α·前 で混ぜる(α=0.5 が既定)。
メカニズム: ちらつき防止。ただし証拠が出ている限り点数は毎フレーム積まれるので、残留の主因は EMA ではない(§6.3 実験1)。

▼ ミニアプリ: サイレンを途中で止めて、「緊急」がいつ降りるかを見る
10
0.50
上の帯 = 混ぜる前の答え、下の帯 = 混ぜた後の答え(赤=緊急、灰=静穏)。サイレンが止まった次のフレームには「混ぜる前」はすぐ静穏に戻り、「混ぜた後」も α=0.5 なら1〜2フレームで降りる — つまり鳴り続けている限り降りないのは EMA のせいではなく、「鳴っている→加点」のルールしかないせいだと分かります。

A-10. Scene-HGF — 場面は健全か

定義: T2 の診断6本(答えの flip 率、確信のなさ、ルールの矛盾度…)を受け取り、health と STABLE/CHANGING/DEGRADING、エピソード切替(cut)を返す。
メカニズム: 6本を反転して加重平均(health = 0.25·(1−flip率) + 0.15×5本)、3つの EMA で平滑化し、閾値で判定(health<0.30 か drift<−0.08 → DEGRADING / health≥0.45 かつ動きなし → STABLE / それ以外 → CHANGING)。
判断できること(建前): 場面の長期的な健全性。実際の弱点: 材料がすべて「T2 の解釈の落ち着き」由来で、世界そのもの(音源の出入り)を見ていない(§6.3 実験3)。

A-11. T3 — この数分の物語は?

定義: T2 の答えの窓平均(直近数フレームの平均)を取り、優先順位つきの閾値で物語(10種)を選ぶ。どれにも届かなければ「いちばん優勢な場面」から自然な物語に変換(fallback 表)。
メカニズム: 平均→閾値→fallback。Scene の信号は受けない(設計上の遮断 D25)。
判断できること: 場面の流れの要約。できないこと: 「続いている」と「変わった」の区別(平均には方向がない、§6.3 実験4)。

▼ ミニアプリ: 窓平均の「遅れ」と「方向の喪失」を見る
4
上の帯 = 実際の場面(灰=静穏、青緑=雑踏)。下の帯 = T3 の答え(青緑=crowd_tendency)。窓を長くすると安定する代わりに立ち上がりも立ち下がりも遅れること、そして雑踏の「入り口」と「出口」で同じ答えになってしまうことが見えます。

A-12. EPI-CTRL / emit — 統合と出力

定義: 各層の答えを集めて最終出力に確定(deepcopy で凍結)し、T0 の危険度から優先度・前面表示を決める。フィードバック(つまみ・エピソード切替)は次のフレーム専用のバッファに書く — 今のフレームには効かせない(D25。これで「答えを見てから答えを変える」循環を構造的に断つ)。emit は出力契約(スキーマ)への適合を検証してから出す。
判断できること: 「どの答えをどの優先度で外に出すか」。
