### R1: addressing 再設計 — `near_prox ∧ speaking_link → addressing_user += 2.5`（near_user より優先）

**コメント**: ADR 0016 決定2（`decisions/0016-f008-relation-rules.md:40-41`）の「`near_prox(min_range<3m) ∧ speaking_link≥1 → addressing_user += 2.5`。これにより near_user(+1.5)より addressing(2.5)が優先される」と一致。near_user の重みは `_W_NEAR_USER = 1.5`（`:48`）で `if conv_strong: logits[NEAR_USER] += 1.5`（`:88-89`）。両者が同時発火しても addressing 2.5 > near_user 1.5 で argmax は addressing になる。AND 条件（`near_prox and speaking_link`）も決定2 の「∧」と一致。テスト `tests/test_F008_relation_rules.py:61-70`（near_prox∧speaking_link → addressing）/ `:73-86`（conv_strong で near_user 1.5 が立っても addressing 2.5 が勝つ）/ `:89-99`（near_prox 単独では非発火）/ `:102-108`（speaking_link 単独では非発火）で AND 条件と優先を境界で固定。

### R2: 既存 addressing（call_user ∨ linked_addressing>0.3）の保持 と 二重発火しないこと

**実現箇所**: `src/supreme/relation.py:95-100`
```python

    if call_user or linked_addressing > _LINKED_ADDRESSING_THRESHOLD:
        logits[ADDRESSING_USER] = logits.get(ADDRESSING_USER, 0.0) + _W_ADDRESSING
    # addressing_user: 【F-008 新規】near_prox ∧ speaking_link。

```
**判定**: 実装済（二重発火しない）
**コメント**: ADR 0016 決定2（`:42`）「既存の `call_user ∨ linked_addressing>0.3 → addressing += 2.5` も保持」と一致。**二重発火の重点確認**: 既存系統（`if`）と新規系統（`elif`）は `if … elif …` の排他分岐であり、両系統が同時に真でも `if` のみが実行され `elif` は評価されない。よって addressing_user に乗る加算は最大でも +2.5 一度であり、**両系統成立でも 2.5 が二度乗ることはない**（仮に独立 `if` 2本なら +5.0 になりうるが、実装は `elif` で排他化しているため起きない）。テスト `:152-162`（call_user → addressing 2.5）/ `:165-172`（linked_addressing 0.5 → addressing 2.5）が既存系統の発火値を 2.5 で固定。観点1 指定の「両系統成立でも +2.5 一度」は `elif` 構造で構造的に保証されている。

### R4: 既定強化 — 4 relation logit が全て 0 のときのみ grouped 既定 += 2.0（他 logit が立つときは既定が立たない＝grouped 二重加算なし）

**実現箇所**: `src/supreme/relation.py:109-112`
```python
    # grouped: 【F-008 既定強化】4 relation logit が全て 0 なら grouped 既定 += 2.0。
    # B1 等で grouped が既に立っている場合は「全て 0」でないため既定は加えない。
    if not logits:
        logits[GROUPED] = _W_GROUPED_DEFAULT
```
重み定数: `:53`（`_W_GROUPED_DEFAULT = 2.0`）。
**判定**: 実装済
**コメント**: ADR 0016 決定3（`decisions/0016-f008-relation-rules.md:49`）「既定強化: 無証拠既定 grouped を 1.0 → 2.0」と一致。**「全 logit 0」条件の重点確認**: `relation_logits` は発火した relation のみを `logits` dict のキーとして持つ純関数（docstring `:25-26` / `:66-67`）。したがって `logits` が空 dict ⇔ near_user/approaching/addressing_user/grouped のいずれも発火していない ⇔ 「4 relation logit が全て 0」と**論理等価**。`if not logits`（dict が空）はこの「全 logit 0」を正確に検出する。conv_strong で near_user が立つ、approaching が立つ、B1/n_speaking_links で grouped が立つ、いずれかが起きれば `logits` は非空となり既定は加算されない。とりわけ B1 で grouped が既に 2.0 立っている場合、`if not logits` は偽となり**grouped に既定 2.0 がさらに乗る二重加算は起きない**（grouped は 2.0 のまま）。テストで多面的に固定:
- 全証拠なし → grouped 既定 logit ちょうど 2.0（`tests/test_F008_relation_rules.py:221-233`・値を直接アサート。argmax だけでは 1.0/2.0 を区別不能なため値で検証）
- 全証拠なし → 他 relation は全て 0（`:236-244`・既定強化発火の前提）
- conv_strong 単独 → near_user が立つので grouped は 0 のまま（`:131-145`・「near_user が立っているのに既定強化が発火している」を明示的に否定）
- approaching 単独 → approaching が立つので grouped は 0 のまま（`:270-286`・approaching を割らない＝w=2.0 が最適点の符号化）
- multiple_humans 単独 → grouped は B1 の 2.0 ちょうど（`:191-201`・「無証拠既定ではなく B1 発火」。値が 2.0 で一致するため二重加算なしを値で固定）

これにより観点1 指定の「conv_strong/approaching/B1 で他 logit が立つときは既定が立たない（grouped 二重加算なし）」が全数で確認できる。

**コメント**: ADR 0016 決定3（`:48`）「B1: `multiple_humans(humans≥2)` → grouped += 2.0」と一致（重み 2.0・`humans≥2` の意味論を `multiple_humans` ブール証拠で受ける）。既存 `n_speaking_links >= 2 → += 1.0` は baseline `t2.py` の grouped ロジック（F-005 で「grouped（n_speaking_links）に直接配線済み」と確認・`reports/erroran-20260612-F005.md:300`）を保持したもので、ADR 0016 が決定3 を「grouped 較正（B1 + 既定強化）」と表現する中の baseline 既存ロジックの保全にあたる。これら2系統は独立 `if` だが、B1 と n_speaking_links は別証拠（humans 数 vs 発話リンク数）であり、両方真なら grouped に 1.0+2.0=3.0 が乗る合算は意図された加点（同一証拠の二重計上ではない）。テスト `tests/test_F008_relation_rules.py:191-201`（multiple_humans → grouped 2.0）/ `:204-213`（multiple_humans 単独では near_user/approaching/addressing_user を発火させない）で B1 を固定。

### R6: argmax の決定性（固定順・乱数なし）

**実現箇所**: `src/supreme/relation.py:117-142`（`classify`）、tie-break 固定順は `:59`
```python
_LABEL_ORDER = (ADDRESSING_USER, NEAR_USER, APPROACHING, GROUPED)
...
    best_label = None
    best_value = None
    for label in _LABEL_ORDER:
        if label not in logits:
            continue
        value = logits[label]
        if best_value is None or value > best_value:
            best_label = label
            best_value = value
    return best_label
```
**判定**: 実装済
**コメント**: ADR 0016「影響」（`:62`）「テストは…argmax の決定性」を符号化。argmax の反復が `_LABEL_ORDER`（固定タプル `:59`）の順で回るため、**dict の挿入順・反復順に依存しない**（`logits.items()` ではなく固定順タプルを反復）。厳密 `>` のため、同値タイが起きた場合は `_LABEL_ORDER` の**先着**（addressing_user > near_user > approaching > grouped の順）が勝つ＝決定的。乱数（random/numpy/torch）・時刻（time/datetime）の参照は皆無（grep 検証済み・後述「決定性」）。ADR 0016 の固定ケースは全て一意 argmax（tie が起きない・test docstring `:37-40` 明記）だが、実装は念のため固定順 tie-break を備える。テスト `tests/test_F008_relation_rules.py:293-324`（代表9点で classify と relation_logits を2回呼び完全一致）で決定性を固定。

## 配線追加でないことの確認（観点1 の重点・ADR 0013/F-005）

**判定**: 配線追加ではない（既存証拠の発火条件再設計である）

- ADR 0013（`decisions/0013-u1-improvement-allocation.md:22`・`:47`）と SPEC F-008 注記（`specs/SPEC.md:159`）は「配線漏れ仮説は F-005 で棄却・改良は配線追加でない」と確定済み。`reports/erroran-20260612-F005.md:297-302` が仮説を [x] 棄却（verdict）し、「`utter_events`/`links` は addressing_user/grouped に直接配線済み・改良の方向は発火条件・優先度の再設計」と結論。
- 実装は R1 の新ルールで `speaking_link`（発話リンク＝既存証拠）と `near_prox`（近接＝既存証拠）の **既存証拠の組み合わせ条件を再設計**したものであり、新たな証拠キーを relation に「配線」する追加ではない。証拠抽出（PSO→特徴）はスコープ外で（決定1）、relation.py は evidence dict を**引数で受け取る**のみ（`:62` `def relation_logits(evidence)`・`:117` `def classify(evidence)`）。
- relation 層が「mode ルールの副作用として各1箇所でしか発火しない」という旧仮説の構造（F-005 `:281`）も、実装が relation 専用の logit ルール（near_user/approaching/addressing_user/grouped の5系統の加点）を独立に持つことで否定されている。ADR 0016 決定2 の括弧書き（`:41`「配線追加ではない＝speaking link は既存・発火条件の再設計」）どおりに符号化されている。

## スコープ遵守（観点2・ADR 0016 決定1・4）

**判定**: 適合

- **証拠抽出（段1・PSO→特徴）を実装していない**: `relation_logits(evidence)`/`classify(evidence)` は evidence dict を**引数で受け取る**のみ（`src/supreme/relation.py:62`・`:117`）。PSO 入力のパース・near_prox/speaking_link/conv_strong 等の特徴を**生成する**コードは存在しない（`:76-83` は `evidence.get(...)` で外から渡された値を読むだけ）。docstring（`:4-5`）が「PSO 入力からの証拠抽出（段1）・温度 softmax・EMA 平滑化は上流の共有基盤でありスコープ外（ADR 0016 決定1）」と明記し、コードもそのとおり。ADR 0016 決定1（`decisions/0016-f008-relation-rules.md:31-35`）に適合。
- **温度 softmax / EMA を実装していない**: 指数化・温度・移動平均・事後確率分布のコードは無い（`:85-114` は加算・比較のみ）。出力は relation logit 群（dict）と argmax ラベル1個。ADR 0016 残件（`:75`）「EMA/softmax 平滑化は baseline 由来。F-008 は logit ルールのみ」に適合。
- **approaching→grouped 9件（上流 T1）の是正に手を出していない**: approaching 入力=False の系を救済する relation 層の補償ロジックは無い。approaching は `approaching` フラグ（上流 T1 由来）でのみ発火（`:92-93`）。ADR 0016 決定4（`:54-55`）の「relation 層で原理的に取れない・T1 改良の別課題として申し送る」に適合。
- **departing/unrelated の語彙追加に手を出していない**: ラベル定数は4クラスのみ公開（`:38-41`）。departing/unrelated を出力・公開する経路は無い。ADR 0016 決定4（`:56`）「勝ち GT が無く是正0のため語彙追加しない」に適合（後述「語彙整合」で再確認）。
- **baseline 再計測は研究者手動**: relation.py に baseline 実走・再計測のコードは無い（ADR 0006 `:33`・研究者の手動領分）。logit 重み 2.5/2.0 は定数として保持（`:48-53`）し、supreme 独立実装後の分布での最終確認は F-013（ADR 0016 残件 `:74`）。

## オーバー実装の検出（観点3）

**判定**: なし（仕様にない実装は検出されなかった）

- **学習なし**: モデル・パラメータ学習・データ読み込みのコードは無い。ADR 0013（`decisions/0013-u1-improvement-allocation.md:36`）「ルール改良項目（mode/relation/quality）は学習しない（param 予算を消費しない）」、ADR 0016 背景（手段＝ルール改良）に適合。
- **契約外機能なし**: 公開シンボルは `relation_logits` / `classify` と定数 `ADDRESSING_USER` / `NEAR_USER` / `APPROACHING` / `GROUPED` のみ（`:38-41`・`:62`・`:117`）。ロギング・設定・I/O・キャッシュ・状態・確認カウンタ等の付随機能は無い。純関数（`:25` docstring「決定的（乱数・時刻なし）な純関数」）で副作用なし。
