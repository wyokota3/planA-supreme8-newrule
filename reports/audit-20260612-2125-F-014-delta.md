### 指摘#3 / ADR 0008 決定3: 窓境界（半開区間 [issued_ts, revoked_ts)）

**初回指摘**: `_within_token_window` の docstring は半開区間と記すが、コードは `ts > revoked_ts` のみ除外で `ts == revoked_ts` が窓内（閉区間）。文書とコードの矛盾＋境界テスト不在。

**実装（コード⇔docstring整合）**: `src/supreme/guard.py:221-231`
```python
def _within_token_window(token, ts) -> bool:
    """ts がトークンの有効期間 [issued_ts, revoked_ts) 内か（半開区間・ADR 0008 決定3）。
    下端は閉（ts == issued_ts は窓内）、上端は開（ts == revoked_ts は窓外＝fail-closed 側）。
    ...
    if ts < token.issued_ts:
        return False
    if token.revoked_ts is not None and ts >= token.revoked_ts:
        return False
    return True
```
**比較演算子が `>=` に修正**され（旧 `>`）、`ts == revoked_ts` は窓外＝不合格になる。docstring の半開区間宣言とコードが一致。

**両端境界テスト**:
- 下端閉（ts==issued_ts は窓内）: `test_F014_seal_token.py:334-338`（is_access_allowed）、`:353-359`（audit）
- 上端開（ts==revoked_ts は窓外）: `test_F014_seal_token.py:341-350`（is_access_allowed=False）、`:362-372`（audit 不合格）
- 上端直下（ts<revoked_ts は窓内・対照）: `test_F014_seal_token.py:375-385`（199.999 で合格）

**注（コード重複の整合確認）**: 窓判定ロジックは `is_access_allowed`（`guard.py:203-214`、未失効なら ts>=issued_ts のみ）と `_within_token_window`（`guard.py:221-231`、失効時刻つき）の2箇所にある。両者は意味的に整合する（is_access_allowed は `not token.active` で失効後を一律 False にするため、未失効トークンの上端 +inf を扱い、失効後の上端境界は audit 側の `_within_token_window` が担う）。境界テストが is_access_allowed と audit の双方を固定しているため、この二重実装によるズレは無い。

**判定: 完全解消**。半開区間でコード・docstring・テストが三点整合。

### 指摘#7（推奨#7前段） / ADR 0008 決定7: cap 不正値の checked=True 不合格（①と同形）

**初回指摘**: `check_trial_cap` が cap=-1・cap=0.5・cap=True を有効上限として比較に使う（①の k 検証との非対称）。

**実装**: `src/supreme/guard.py:343-347`
```python
    if not _is_nonneg_int(cap):
        return GuardResult(
            passed=False, guard_id=guard_id, checked=True,
            reason=f"不正値: 上限 cap={cap!r} は非負整数でない（無効な上限・fail-closed で不合格）。",
        )
```
cap の不正値検証が `trial_count` 検証より**前**に置かれ（`guard.py:343` が `:349` の trial_count 検証に先行）、`checked=True`・`passed=False`。`_is_nonneg_int`（`guard.py:104-106`）は bool を除外するため cap=True も不正値になる。cap=None の `checked=False`（`guard.py:337-341`）とは明確に区別。

**test-writer 報告の「偽 green の強化」（trial_count=0 を使う形）が実際に偽 green を排除しているかの検証**:
- cap=-1 のテスト: `test_F014_trial_cap.py:126-141`。`trial_count=0, cap=-1` を使い、`assert ("不正" in r.reason) or ("無効" in r.reason) or ("invalid" in ...)` を要求（`:141`）。docstring（`:132-135`）が「cap=-1 を正当な上限として素通り比較すると 0 <= -1 は False で偶然不合格になるが、それは『上限超過』扱いであり不正値検出ではない。…reason 不一致で red になる」と明記。**実装の reason は「不正値: 上限 cap=-1 は…」（`guard.py:346`）なので「不正」を含み green。一方、もし cap 検証を欠いた旧実装に戻すと、0<=-1 で passed=False にはなるが reason は「不合格: trial_count=0 > cap=-1（撤退基準④・上限超過）」（`guard.py:359` 経路）で「不正/無効/invalid」を含まず red になる。よって偽 green は排除されている**（trial_count=0 を使う設計が、単なる「上限超過での偶然の False」をパスさせない強化として機能している）。
- cap=True のテスト: `test_F014_trial_cap.py:155-167`。`trial_count=0, cap=True` で、bool を 1 として `0 <= True(1)` を True 扱いする fail-open を red 化（docstring `:161-163`）。実装は `_is_nonneg_int` で bool 除外のため passed=False で green。
- cap=10.5 のテスト: `test_F014_trial_cap.py:144-152`。`trial_count=5, cap=10.5` で、非整数 cap を有効上限とすると `5 <= 10.5` で合格になる fail-open を red 化。実装は非整数で不合格 green。

**判定: 完全解消**。cap 不正値（負数・非整数・bool）は①の k 検証と同形に checked=True 不合格。trial_count=0 を使う「偽 green の強化」は意図どおり機能し、cap 検証を外すと該当3テストが red になる構造になっている。

### F-014-2: 封印アクセスの開封トークン期間外検査・事前検査合格時発行・F-013終了で失効
**判定: 「部分的に実装」→「実装済」へ更新**。

- (i) 既定 production=False による「生涯1回」の既定無効 → **決定1で既定廃止・明示必須化**（`guard.py:168`）。silent fail-open を型レベルで排除。
- (ii) `lifetime_session_count()` を1と突合する監査関数の不在 → 初回の懸念は「多重発行を発行時に止める以外の防衛線がない」点だったが、**決定2で正規発行経路が `open_token_for_eval` に一意化され、production=True 内包時は発行経路が必ず生涯1回制約に従う**（`test_F014_block_downstream.py:256-267`）。発行経路が一本化されたことで、`lifetime_session_count()` を別途突合する監査関数が無くても「発行時に必ず止まる」防衛線が機能する（後述の残存リスク参照）。
- (iii) F-013向け経路が SealGuard を経由せず計数しない → **決定2で `open_token_for_eval` が内包 SealGuard 経由・計数消費**（`guard.py:442-444`、`test_F014_block_downstream.py:231-241`）。
加えて窓境界（決定3）・revoked_ts必須化（決定4）も解消。ADR 0002 の②定義「有効トークン期間外0件 ∧ 生涯開封セッション数1」のうち、後半「生涯1回」が既定で有効化され、正規経路で必ず消費されるため、**条文・ADR 0002 定義の双方に対し実装済と判定できる**。
