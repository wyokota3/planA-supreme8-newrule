### F-001-1: 封印セットの全親系統IDが、練習用・増強の親系統IDリネージ集合と交わらない(集合演算で assert)
**実現箇所**: `src/supreme/datagov.py:509-533`
```python
    def lineage_set(self, split):
        """指定 split に属するレコードの root 親系統ID集合を返す。

        子孫は推移閉包で root へ畳まれる(孫経由リーク検出の前提)。
        """
        roots = set()
        for sid, s in self._split.items():
            if s == split:

        train_roots = self.lineage_set("train")
```

例外定義は `src/supreme/datagov.py:29-31`(`LineageCrossError`)。SPEC F-001 異常系「分割が親系統を跨いだ場合は払い出しを拒否しエラー化」(SPEC.md:66)に一致。SPEC 境界条件「孫・ひ孫は推移的に親系統へ畳む」(SPEC.md:67)は `lineage_set` が `resolve_root`(後述)経由で root に畳むことで実現。

## 未検査領域(implementer 自己申告)の評価: `meta.parent_lineage_id` の値整合

**事実関係**:
- `validate_record` は `parent_lineage_id` の**型(str)のみ**検査(datagov.py:158-164)
- `register` の親系統検査は「root 宣言(parents=[] ∧ parent_lineage_id=自身 ∧ generation=0)」か「parents 全員が登録済み」かのみ(datagov.py:429-437)。宣言された `parent_lineage_id` の値が実際の root と一致するかは**どこでも検査されない**
- さらに副作用として、`parents=[]` だが `parent_lineage_id ≠ 自身` のレコードは root 宣言でないのに登録が通る(429-437 の論理: 非 root 宣言でも空 parents ならループが回らない)

**GT_SCHEMA の要求範囲か、仕様の穴か**: **仕様の穴**と判定する。GT_SCHEMA.md:67 の拒否表の字義(「親系統不明=parents の参照先が未登録、かつ root 宣言でもない」)に対しては実装は適合しており、implementer の字義解釈は正当。しかし GT_SCHEMA.md:19 は `parent_lineage_id` を「root(親系統)の scenario_id」と定義し、:98 で「親の parent_lineage_id を**継承**」と規定する。値の正しさはスキーマの意味論上の要求であるのに、拒否表に値整合の規則が無く、検査主体も未指定。契約の表と本文が噛み合っていない。

**リスク評価: 中**。
- F-001 内部では安全: `lineage_set`/`payout`/`assign_split` はすべて `resolve_root`(parents 連鎖)基準で root を計算し、保存された `parent_lineage_id` を一切参照しない(datagov.py:509-518, 583-589)。したがって F-001 の非交差保証そのものは虚偽値に汚染されない
- 下流では危険: F-002-1(封印の非交差)・F-003(親系統タグ付与)の実装が `meta.parent_lineage_id` を**直接読む**実装になった場合、虚偽値が封印リークの経路になる。前述の「parents=[] 非 root 宣言」の抜け道と組み合わさると「root でないのに root 扱い」のレコードが正規に登録できる
- 緩和条件: 登録時点で親は登録済みのため、検算(`resolve_root` 相当)は登録時に計算可能。修正コストは低い

## 推奨アクション
1. **優先度 高(F-002 着手前)**: `register` に `parent_lineage_id` の検算(宣言値 = parents 連鎖から計算した root)と「parents=[] なら root 宣言の3条件を強制」を追加するか、GT_SCHEMA.md の拒否表に値整合規則を追記して実装を追随させる。いずれも GT_SCHEMA 改版+ADR 記録(ADR 0003 の改版規定)を伴うこと
2. **優先度 高**: 同一 `scenario_id` 再登録のサイレント上書き(datagov.py:439)の仕様化(拒否 or 版管理)。リネージの事後改変が可能な現状は「データ規律基盤」の趣旨に反する
