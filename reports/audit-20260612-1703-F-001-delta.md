## 前回指摘の解消判定(引用付き)

### 指摘1: parent_lineage_id・generation の検算(非rootの解決値一致)

**前回**: `validate_record` は `parent_lineage_id` の型(str)のみ検査。`register` も親の登録有無のみ検査し、
宣言値が実際の root/世代と一致するかをどこでも検査しない(初回監査:170-174)。

**修正後の実装箇所**: `src/supreme/datagov.py:487-509`(`register` 内、非 root 経路)

```python
parent = parents[0]
resolved_root = self.resolve_root(parent)
resolved_generation = self.generation_of(parent) + 1
if meta["parent_lineage_id"] != resolved_root:
    raise ValidationError(
        f"parent_lineage_id checksum mismatch for {sid!r}: ...")
if meta["generation"] != resolved_generation:
    raise ValidationError(
        f"generation checksum mismatch for {sid!r}: ...")
```

- 親は登録済み(`datagov.py:481-486` で未登録なら `LineageError`)であるため、登録時点で
  `resolve_root`/`generation_of` による解決値が計算可能。宣言値と解決値の不一致を `ValidationError` で拒否。
- 改版 GT_SCHEMA の拒否表「`parent_lineage_id`・`generation` の検算不一致(`parents` 連鎖から解決した値と不一致)」
  (`GT_SCHEMA.md:67`)および本文 `GT_SCHEMA.md:100` と字義一致。

**テスト**: `tests/test_F001_schema_validation.py:267-306`
- `test_F001_2_nonroot_parent_lineage_id_checksum_mismatch_rejected`(:267-286、`parent_lineage_id="WRONG_ROOT"`)
- `test_F001_2_nonroot_generation_checksum_mismatch_rejected`(:289-306、`generation=7` を連鎖深さ1に対し宣言)

**判定**: **解消**

### 指摘2: root宣言の抜け道(parents=[] ∧ parent_lineage_id≠自身)

**前回**: `parents=[]` だが `parent_lineage_id ≠ 自身` のレコードは root 宣言でないのに登録が通る
(空 parents だと register のループが回らず `LineageError` に到達しない。初回監査:172、:144)。

**修正後の実装箇所**: `src/supreme/datagov.py:194-212`(`_validate_meta` 内、root 宣言3条件の検査)

```python
if (isinstance(parents, list) and parents == []
        and isinstance(sid, str) and isinstance(plid, str)
        and isinstance(gen, int) and not isinstance(gen, bool)):
    if plid != sid:
        errors.append("root declaration inconsistent: parents=[] but "
            f"parent_lineage_id ({plid!r}) != scenario_id ({sid!r})")
    if gen != 0:
        errors.append("root declaration inconsistent: parents=[] but "
            f"generation ({gen!r}) != 0")
```

- `parents=[]` を root 宣言とみなし、`parent_lineage_id=自身 ∧ generation=0` を強制。違反は `validate_record`
  の `errors` に積まれ、`register` は `result.ok` 偽で `ValidationError`(`datagov.py:459-461`)。
- この検査は `validate_record` 段(register の先頭で呼ばれる `datagov.py:459`)で発火するため、抜け道だった
  「非 root 宣言でも空 parents ならループが回らない」経路に到達する前に拒否される。3条件強制が成立。
- 改版 GT_SCHEMA「root 宣言の不整合(`parents`=[] なのに `parent_lineage_id`≠自身 または `generation`≠0)」
  (`GT_SCHEMA.md:67`、本文 `GT_SCHEMA.md:98`)と字義一致。

**テスト**: `tests/test_F001_schema_validation.py:230-262`
- `test_F001_2_root_decl_empty_parents_with_foreign_lineage_id_rejected`(:230-245、`parent_lineage_id="SOMEONE_ELSE"`)
- `test_F001_2_root_decl_empty_parents_with_nonzero_generation_rejected`(:248-262、`generation=5`)

**判定**: **解消**

**前回**: 同一 scenario_id の再登録はサイレント上書き(`datagov.py:439`)。リネージの事後改変が可能で

### 指摘4: set_split の完全削除 / register の meta.split 受理 / payout の防御的検証

**前回**: 手動分割 `set_split(scenario_id, split)` がオーバー実装(`datagov.py:502-507`)。交差する split を
作れる footgun(初回監査:162、:10)。

**(a) set_split の完全削除**:

- DataGovernor のメソッドは `register`/`resolve_root`/`generation_of`/`lineage_set`/`payout`/`assign_split`/
  `assignment_history` のみ(`datagov.py:453,517,544,578,589,606,669`)。`set_split` はクラスにもモジュール直下にも無い。
- `datagov.py:574` の `set_split` 言及は削除を説明するコメント(実コードでない)。
- 回帰テスト: `tests/test_F001_lineage_disjoint.py:142-155`
  `test_F001_1_set_split_is_removed` が `not hasattr(gov, "set_split")`(:150)と
  `not hasattr(datagov, "set_split")`(:153)の双方を assert。クラス・モジュール双方の不在を担保。

**(b) register の meta.split 受理**: `src/supreme/datagov.py:512`

```python
self._split[sid] = meta.get("split", "unassigned") or "unassigned"
```

- `register` が `meta.split` をそのまま受理(空/欠落は `unassigned` 既定)。違反状態の構成は
  `tests/fixtures_gt.py:131-140` の `with_split`(meta.split を上書きして register するデータ駆動方式)で行う。
- 改版 GT_SCHEMA「`register` は `meta.split` をそのまま受理する(既定 `unassigned`。取込・状態復元・テストでの
  違反状態構成用)」(`GT_SCHEMA.md:113`)と一致。

**(c) payout の防御的非交差検証**: `src/supreme/datagov.py:589-602`

```python
def payout(self, split):
    seal_roots = self.lineage_set("seal")
    train_roots = self.lineage_set("train")
    if seal_roots & train_roots:
        raise LineageCrossError(...)

```

- 割当の経路(assign_split / register の meta.split)に関わらず、払い出し時に root 単位
  (`lineage_set` は `resolve_root` で畳む、`datagov.py:578-587`)で非交差を防御的に検証。
- 改版 GT_SCHEMA「`payout` は割当の経路に関わらず非交差を**防御的に**検証する」(`GT_SCHEMA.md:114`)と一致。
- 違反検出テスト: `tests/test_F001_lineage_disjoint.py:72-88`(同根を seal/train に分けて `LineageCrossError`)、
  孫経由リーク :90-113。陰性対照 :116-139。いずれも `with_split` データ駆動方式に書き換え済み。

**判定**: **解消**(削除・受理・防御検証の3点すべて GT_SCHEMA 記述どおり)
