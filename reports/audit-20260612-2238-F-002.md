## 【最重点】生涯計数のプロセス跨ぎ復元 — `SealGuard._lifetime_session_count` への private 書き込み

該当コード `src/supreme/sealset.py:321-326`:
```python
        state = json.loads(self._state_path.read_text(encoding="utf-8"))
        count = state.get("lifetime_session_count", 0)
        # 内包 SealGuard の生涯計数フィールドを復元する。SealGuard は計数を
        # _lifetime_session_count に保持する（guard 契約・同一プロセス内 R4 を
        # 永続状態で補完する F-002 の責務）。
        self._guard._lifetime_session_count = count
```
guard 側の private 実体: `src/supreme/guard.py:171`(`self._lifetime_session_count = 0`)、参照 `:183`(発行制限)・`:218`(`lifetime_session_count()`)。

### (a) 正しさ

- **復元タイミング**: `__init__`(`sealset.py:98`)で発行可能になる前に復元。同一インスタンス内で発行→永続化(`:227`)の順序も正しい。**逐次運用(単一プロセス・単一インスタンス)では正しい**。テスト `test_F002_lifetime_session.py:81-98`/`:101-110` がプロセス跨ぎの核心を固定している。
- **production/dummy 整合**: 復元は両モードで走るが、制限判定は `guard.issue_token` の `self.production` 分岐(`guard.py:183`)のみで効くため、dummy の複数回開封(`test_F002_lifetime_session.py:132-139`)と矛盾しない。整合。
- **競合(未保証)**: 同一 root_dir を指す2インスタンスが**並行**に存在すると、双方が count=0 を復元→双方が発行成功→ `session_state.json` は最終書込の「1」になり**実セッション数2を過少計上**する。ロックなし・compare-and-swap なし。緩和: 両セッションは access_log に別 session_id で残るため `audit_seal_access` の事後突合(`test_F002_access_log.py:221-250` が経路を実証)で**検出は可能**。ただしこの「単一書き手前提」はどこにも文書化されていない。
- **外部注入 guard との相互作用**: `seal_guard` を外部注入した場合(`sealset.py:92-94`)、ディスク状態が注入 guard のインメモリ計数を**上書き**する(状態ファイルが古いと計数が巻き戻る=fail-open 方向)。状態ファイル不在時は何もしない(`:319-320`)ため、**SearchGate 経由で発行された計数は永続化されない**(後述 G2)。
- **入力検証なし**: 復元値の型・非負検査がない(`:322`)。`"lifetime_session_count": 0` への手動改竄で2回目発行が通る(fail-open。検出は access_log 突合のみ)。文字列等の型不正は次回発行時の比較で TypeError(fail-closed 側のクラッシュ)。

### (b) 結合リスク

- guard が private 属性名を変更すると復元が**黙って無効化**され、本番封印の生涯1回がプロセス跨ぎで破れる(fail-open)。ただし `test_F002_2_production_second_issue_rejected_across_instances`(`test_F002_lifetime_session.py:81-98`)が CI でこの退行を**検出する**ため、「サイレント破壊」ではなく「テストで止まる破壊」。リスクは結合そのものより、**GUARD_IF にこの依存が一行も書かれていない**こと(GUARD_IF は R4「生涯計数はインメモリ・運用規約2 で補完」と書くのみで、補完の実装手段=private 書き込みは契約外)。guard の implementer が GUARD_IF だけ見てリファクタすると F-002 テストの失敗で初めて気づく構図。

### (c) 推奨対処

推奨は **guard への公開復元APIの追加(F-014 の小改修)+GUARD_IF 追記**:
- 案: `SealGuard(*, production: bool, initial_session_count: int = 0)`(構築時注入・非負整数検証付き)。guard の「時計・乱数を持たない決定的設計」と整合し、稼働中の計数巻き戻し(任意時点 setter の危険)も構造的に避けられる。sealset 側は `__init__` で状態ファイルを先に読み、guard 生成時に渡す形に変える(外部注入 guard との優先順位規約も同時に定義)。
- 次善(現状容認)の場合は最低限: GUARD_IF に「F-002 が `_lifetime_session_count` を復元する(変更時は F-002 改修必須・回帰検知は test_F002_lifetime_session)」を**注記**し、`_restore_session_state` に復元値の型・非負バリデーションを追加する。
- いずれを選んでも、後述 **G2(SearchGate 合成)は解決されない**ので別途必要。

## 封印保全の抜け穴探索

### ① `stored_meta`(トークン無し参照可)からの間接漏洩
`sealset.py:205-211` は `body["meta"]` のみ返す。meta のキー(scenario_id/source/parent_lineage_id/parents/generation/split/gt_origin/registered_at — GT_SCHEMA 正規形)に gt 由来の値は含まれない。`sealed_lineage_set`(`:183-201`)も root ID のみ返す。**漏洩なし**。ただし両APIは body ファイル全体(gt 含む)をプロセス内に読み込む実装(`:179`, `:195`)であり、返却値には乗らない。meta 参照は access_log に記録されない(「秘匿対象は gt 本体のみ」をテスト `test_F002_schema_and_storage.py:178-185` が契約化)。

### ② `register` の戻り値・例外メッセージへの gt 混入
- `RegisterResult`(`sealset.py:51-61`, `:147-152`): scenario_id/split/gt_origin/warnings のみ。warnings は datagov 由来だが、対象は**呼び出し側が今持っている入力レコード**であり封印済みデータではない(漏洩概念に該当しない)。
- 例外: `ValidationError`(`:123`・入力自身の検査結果)、`LineageCrossError`(`:133-136`・root ID のみ)、`AccessDenied`(`:260-262`・scenario_id と ts のみ)。**gt 本体の混入なし**。

### ③ access_log 記録の例外経路網羅性(拒否→記録の順序・記録失敗時)
- **拒否経路**: 記録(`:257-259`)→例外送出(`:260-262`)の順。**記録が先**であり正しい(例外で記録がスキップされない)。テスト `test_F002_abnormal.py:53-96` が検出・記録・拒否と再起動後の監査残存を固定。
- **成功経路**: 記録(`:249-252`)→本体読出(`:253`)の順。**記録なしの読出は構造的に不可能**。なお記録後に `_load_body` が KeyError(対象不存在)になる場合、実読出なしのレコードが残るが過剰記録方向(安全側)。
- **記録失敗時(限界)**: `_append_log` が I/O エラーを出すと、成功経路では gt は返らず(fail-closed)、拒否経路では `AccessDenied` の代わりに OSError が伝播し**その試行は無記録**になる。データは漏れないが「全アクセス試行を記録」(ADR 0009 決定2)が I/O 障害下では成立しない。**未文書化** — 既知限界として明記推奨。

### ④ `session_state.json` の手動改竄への耐性
- count を 0 に書き戻せば2回目発行が通る(**fail-open**)。検出可能性: 両開封セッションが access_log に別 session_id で残る限り、`audit_seal_access` 突合(GUARD_IF 運用規約2)で**事後検出可能**。ただし access_log 自体の行削除・改竄は検出不能(後述「永続ログの品質」)。
- 文書化状況: ADR 0009 決定2 は穴8 を「**ログを介さないファイル直読み**」についてのみ既知限界と明記。**状態ファイル改竄・ログ改竄は明記されていない**。穴8 と同種の限界(技術ロック未設計・自己申告ファイルへの依存)だが、現状は**文書化が部分的** — ADR または GUARD_IF/ADR 0009 への追記を推奨(対処は文書化で可、暗号化等の実装は ADR 0009 の却下決定に従い不要)。

### ⑤(本監査での新規発見・最重要)`register` による封印済みレコードの上書き
`sealset.py:139-145`:
```python
        self._ensure_sealed_dir()
        stored = json.loads(json.dumps(record))  # deep copy（呼び出し側の改変から守る）
        stored["meta"]["split"] = "seal"
        gt_origin = stored["meta"]["gt_origin"]
        self._body_path(sid).write_text(
            json.dumps(stored, ensure_ascii=False), encoding="utf-8"
        )
```
既存ファイルの存在検査がなく、**同一 scenario_id の再 register が封印本体を黙って差し替える**。GT_SCHEMA の拒否表「scenario_id の再登録(リネージ不変性の担保)」に対応する検査は `DataGovernor.register` 側にあり、sealset は governor へ登録しないため**素通り**。穴8(API 外のファイル直書き)と異なり、これは**正規APIによる封印改変**であり、トークン不要・access_log にも残らない。SPEC「学習・調整に不可触」の機構的破れ。テストも存在しない。**修正必須(優先度: 高)** — 既存 `sealed/<scenario_id>.json` が存在すれば拒否(専用例外)+陰性テスト追加。

## GUARD_IF 契約への適合

- **SealAccessRecord 形式**: 適合。成功 `{"session_id": token.session_id, "ts": float(ts), "target": scenario_id}`(`sealset.py:249-251`)、拒否 `session_id=None`(`:257-259`)。GUARD_IF§2 の「有効トークン下=その session_id／トークン無し不正=None」どおり。`guard.audit_seal_access` との突合も実テストで実証(`test_F002_access_log.py:221-250`)。
- **(統合ギャップ G2・高)正規経路の整合が未定義**: GUARD_IF§1 は「`issue_token` はアプリケーションコードから直接呼ばない(R2)。封印開封の唯一の正規経路は `SearchGate.open_token_for_eval`」とする。一方 F-002 は `SealStore.issue_open_token`(`sealset.py:215-228`)として **`issue_token` 直接委譲+自己申告 bool `precheck_passed`** を公開APIに再露出した。これはテスト駆動契約(テスト docstring が要求)なので実装の独断ではないが、**F-013 がどちらの経路を使っても封印保全の核が欠ける**:
  - (a) GUARD_IF どおり `SearchGate.open_token_for_eval`(`guard.py:424-444`)で開封 → SealStore は発行を観測せず `session_state.json` が更新されない → **生涯計数のプロセス跨ぎ保証が消える**(共有 guard を注入しても `_persist_session_state` は `SealStore.issue_open_token` 内 :227 でしか呼ばれない)。
  - (b) `SealStore.issue_open_token` で開封 → 永続化はされるが **AggregateResult による事前検査が素通し**(自己申告 bool)になり、ADR 0008 決定2 が閉じた経路の再開通。
  - 現状の説明可能な整理: `issue_open_token` は guard の R2 と同格の「低レベル操作」(常用テスト・ダミーモード用)であり、本番 F-013 の正規手順は未定義のまま——という解釈は可能だが、**どこにも書かれていない**。推奨: F-013 着手前に「SealStore が SearchGate を内包(または受領)し、aggregate 検査済み発行+永続化を1メソッドで提供する」合成APIを定義し、GUARD_IF/ADR に記録。`issue_open_token` には「本番封印の正規経路ではない」旨の docstring 注記を追加。

## 永続ログの品質

- **追記の原子性**: `open("a")`+1行1 write(`sealset.py:266-270`)。fsync なし・プロセスクラッシュで行途中破損があり得るが、**破損行は読み戻し時に必ず `LogCorruptionError`**(不正 JSON: `:285-290`)になり黙過されない(途中切断された JSON は閉じ括弧を欠き必ず不正)。検出方針は妥当。
- **LogCorruptionError の検出範囲**: ①不正 JSON 行(`:285-290`) ②非 dict・必須キー欠落(`:291-297`)。**検出しないもの**: (i) キーは揃うが**型不正**な行(例 `target` が int)— SealAccessRecord「型どおり」契約より狭い。`audit_seal_access` も target の型は見ないため改竄行が両検査をすり抜けうる(軽微・型検査の追加を推奨)。(ii) 空行は黙ってスキップ(`:283-284`・レコードでないため許容)。(iii) **行削除・整形済み改竄**は原理的に検出不能。
- **改竄検出の限界の明記**: ADR 0009 は穴8(直読み)のみ明記。**ログ自体の改竄・削除が検出不能である点は明記されていない**(④と同根)。追記推奨。
