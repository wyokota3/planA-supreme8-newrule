巨大ワイヤリングを頭に載せずに、
「どのフレームがなぜ効く/効かないか」を掴む

T0〜T3・HGF・分岐ノードを全部同時に保持する、というやり方は誰がやっても破綻する。これは能力の問題ではなく、 やり方の問題。全体を保持せず、粗→細の望遠鏡（層 → クラス → フレーム）で1層・数フレームずつ見る手順をまとめる。
中核の発想：「何を出すべきか(WHAT)」と「どう計算しているか(HOW)」を分ける。
複雑さのほとんどは HOW（HGF・温度・EMA・分岐＝どう計算するか）に集中する。だが理解と改善に効くのは WHAT（各層が本来出すべき答え）で、 これは驚くほど小さい。採点されるのは8層の出力だけなので、システムは「1つの巨大グラフ」ではなく「8つの独立した “観測→判断” 問題」として切り出せる。 各層について問いは2つだけ：
  Q1（WHAT） GT は何の観測から決まるか？　/　Q2（CAN） その観測は、外しているフレームの入力に在って・曖昧でないか？

診断ループ（粗→細の7ステップ）

1

8層に分解する

「T0がT1にどう繋がり…」を追わない。各層を独立に「この観測からこのラベルを出す」問題として切り出す。HGF も分岐も、Q2 のときだけ覗く内部に格下げされる。

2

gt_derive から「信号インベントリ」を作る

gt_derive.py の各関数（risk_tier/t1_state_seq/relation_seq/mode_seq/quality_regime）は、それぞれ約10行の決定的関数＝「正解の定義」。その関数が触れている入力フィールドだけがその層で意味を持つ信号の全集合。残りの入力はその層に無関係。

層GT が触る信号（＝見るべきもの全部）
risk_tier 観測min_TTC_s / salient kind(siren)
t1_state 観測salient track の r_m 系列（Δr）/ 最接近距離
t2_mode 観測risk / links[].type / salient kind / 生QoS / ΔQoS / utter
t2_relation 観測salient の r_m/Δr / link type / track 数
t2_rolesalient kind（＋ v1.5 salience で human/object 分離）
quality_regime 観測生 QoS（h_q ではない＝循環回避）
t3 / scene intentmode 窓 + episode/stability（意図寄り＝天井あり）

これで「mode を見るのに HGF は要らない、見るのは6観測だけ」と確定する。複雑さが消えるのはこの瞬間。

3

混同行列は「対角」でなく「質量の行き先」を読む

held-out split で GT→pred を層別集計し、低い対角クラスについて質量がどこへ流れたか（off-diagonal の宛先）を読む。宛先が失敗の種類を教える。

  • catch-all へ全部流れる → 死クラス（emit 経路ゼロ）。例: side_rear→alert_required 全件。
  • 兄弟クラスへ流れる → 識別子の取り違え。例: conv_ongoing→conv_request。
  • 既定へ落ちる → クラス自体が未実装。例: departing→grouped。

宛先を見るだけで「死クラス／識別子不足／未実装」のどれかが分かり、打ち手が決まる。

4

分離テスト ＝ 「観測層 vs 天井」を決める核心

外している GT クラスと混同先のクラスで、インベントリの各信号のクラス別分布を並べ、両者を分離する信号が1つでもあるかを見る。要は「観測を1次元に射影して、GTクラスが重ならない軸を探す」。

効く例（env_start）： 生QoSの分散では env_start(振動)も hazard_declining(単調降下)も両方“高分散”で重なる。だがトレンド除去後の残差分散に射影すると env_start=残差大／hazard≈0 で綺麗に割れた。＝正しい射影軸を見つけるのが分離テストの本質。割れた→モデルがその軸を使っていないだけ＝直せる（観測層）。
効かない例（hazard_declining）： TTC一定・QoS単調で、他の降下系クラスと全観測軸で重なる。分離軸が存在しない＝入力に答えが無い（天井）。ここを閾値で押し込むのが過適合（旧0.828の失敗）。“割れない”を確認できたら止めるのが正解。

つまり「なぜ効く」＝分離軸が観測に在ったから。「なぜ効かない」＝どの観測軸でも重なる＝情報が入力に無いから。 これが原理レベルの答え。

5

フレーム単位の「なぜ」＝決定トレースの差分行

最悪の (GT, pred) セルから具体シナリオを2〜3本引き、フレームごとに「決定トレース」を印字する。GT規則を分岐ごとに評価し、モデル出力と並べ、乖離した1行を見る。それがそのフレームの根本原因。

frame pw-021-train-00 #2  生観測: salient=barrier(theta=0)  TTC=5.0(caution帯)  QoS=0.9
GT規則(mode_seq): danger?→no  conv?→no  alarm?→no  BLOCK?→no  Δq?→no
                  vehicle&caution?→no  caution → side_rear_caution ★
モデル出力: caution → alert_required（caution を一律 alert に潰していた）
→ ★ の行で乖離。直し所＝「caution 分岐を salient kind で振り分ける」と一意に決まる。

フレーム数を絞っているので数分の作業。「どのシナリオのどのフレームが効く/効かない」は、この決定トレースを表にするだけで全部出る。

6

ワイヤリング/HGF に降りるのは“最後の一手”だけ

降りる条件は1つ：観測層 ∧ 分離軸が在る ∧ でもモデルが出せていない、かつ境界上書きでなく源流を直したいとき。そのときも全グラフは追わず、1フレームだけパイプラインに通し各ノード出力を印字して、期待とズレるノードを1つ見つける（水滴を1粒だけ追う）。

HGF の捉え方＝「慣性つきの平滑化器」。 効果は遅延・ヒステリシス。だから「採点出力が生観測そのものであるべき層」では HGF が循環/遅延を入れて害になる。実例 quality：GT は“生QoS”なのにモデルは HGF後の h_q で判定し 0.80 に留まっていた。生観測で出力を確定し、HGFは下流gating用に残すのが定石。数式の中身を理解せずとも「役割の取り違え」だけ見れば直せる。
7

本物か（理解 vs 自己欺瞞）を機械判定する

掴んだ「効く理由」が本物かは3点で判定：

  • eval≈train（汎化している。割れたのが偶然でない）
  • 閾値ロバスト（閾値を少し動かしても結果不変＝knife-edge でない）
  • 観測のみ・非循環（GTラベルや自分の出力から逆算していない）

満たさないなら「理解した」でなく「合わせ込んだ」。今回の勝ちは全部この3点を通している。

これがそのまま「アーキの特徴・長短・改善優先順位」の地図になる

③④を全層に回すと、各層が2種類に色分けされる。これがあなたが求めている地図そのもの。

種別層性質と打ち手
rule_derivedrisk / t1 / mode / relation / quality / role(一部)観測の決定的関数。忠実実装で ~1.0 まで行く。低いのは“やり残し”（実装の未完）であって原理的限界ではない。
intent-derivedt3 / scene意図が観測に無い。heuristic 上限（t3 61% / scene 77%）で頭打ち。ここを上げようとするのが過適合の罠。

実際、「supreme の優位は v1.5 入力層に集約」「強baseline の mode が 1.0 まで行く」と言えたのは、すべてこの地図の上での話だった。

まとめ

粗→細の望遠鏡： ①8層に分解 → ②gt_deriveで信号インベントリ → ③混同の質量の行き先で失敗種別 → ④分離テストで観測層/天井を判定 → ⑤決定トレースでフレームの乖離行＝なぜ → ⑥必要時だけ1フレームを配線に通す → ⑦汎化3点で検証。

各ステップは一度に1層・数フレームしか見ない。だから全体を頭に載せる必要が原理的に無い。「能力を超える」感覚は、載せようとしているからであって、この手順なら載せずに済む。

次の一手（提案）

この①〜⑦を、目の前で1層分まわして見せるのが一番腑に落ちる。題材候補：t2_role（baseline 0.57 / supreme 0.96）。③混同 → ④分離テスト → ⑤決定トレースまで実データで出し、「どのシナリオのどのフレームがなぜ効く/効かないか」の表を作る。 そのうえで①〜⑦を「層名と split を渡すだけで回る1つの再利用ツール」に固めれば、把握が「記憶の力技」から「実行して読むだけ」になる。
