`src/supreme/search.py:201-209`

axis_name, value, score = best_move

### 観点3: F-012-3 試行上限(cap=50)+ patience

#### (3-a) trial_count ≤ cap を構造的に保証するか(評価前チェック) — 合格

cap チェックは**評価(scorer 呼び出し)の前**に2箇所で行う。

外側ループ先頭(パス開始前):
`src/supreme/search.py:149-154`
```python
while True:
    if len(trials) >= cap:
        break
    if no_improve_streak >= patience:
        break
```

内側ループ(候補評価の直前):
`src/supreme/search.py:166-173`
```python
if len(trials) >= cap:
    stopped = True
    break
if no_improve_streak >= patience:
    stopped = True
    break
candidate = dict(incumbent)
candidate[axis_name] = value
score = _evaluate(candidate)
```

`_evaluate`(`search.py:124-143`)が `trials.append` する=1試行。評価前に `len(trials) >= cap` で打ち切るため、`_evaluate` 後に `len(trials)` が cap を超える経路が無い。基準構成評価1回(`search.py:146`)は cap ≥ 1 を暗黙前提とするが、テストは cap=12 等を与え `trial_count <= cap` を機械固定(`tests/test_F012_trial_cap.py:65-73`)。広い空間+常時改善 scorer でも `trial_count <= 50` を固定(`tests/test_F012_trial_cap.py:50-62`)。

#### (3-b) check_trial_cap(_, 50) 合格か — 合格

`tests/test_F012_trial_cap.py:76-88` が `guard.check_trial_cap(trial_count=result.trial_count, cap=50)` の `passed is True / checked is True / guard_id == "F-014-4"` を固定。`check_trial_cap`(`src/supreme/guard.py:341-377`)は `trial_count <= cap` で合格する契約(GUARD_IF §1)と整合し、search が cap=50 を超えない限り常に合格する。

#### (3-c) patience=10 の無改善撤退が正しいか — 合格

無改善ストリークは「改善しなかった試行」「ガード不合格でスキップした候補」で加算され、改善採用候補でリセットされる。

`src/supreme/search.py:180-192`
```python
if not _passes_guards(candidate, candidate_guards, search_gate):
    no_improve_streak += 1
    continue
if score > best_score:
    no_improve_streak = 0
    if score > best_move_score:
        best_move = (axis_name, value, score)
        best_move_score = score
else:
    no_improve_streak += 1
```

`no_improve_streak >= patience` で内外ループとも撤退(`search.py:153,171`)。テスト `test_F012_3_early_stop_on_no_improvement_patience`(`tests/test_F012_trial_cap.py:95-110`)が flat scorer で cap(50)より早く撤退(`trial_count < 50`)を固定。`test_F012_3_smaller_patience_stops_sooner`(`tests/test_F012_trial_cap.py:113-125`)が patience 単調性(p3 ≤ p10)を固定。

注(挙動の正確な記述・欠陥ではない): `no_improve_streak` は `best_move`(パス内ベスト)を厳密に上回らない改善候補(`best_score < score <= best_move_score`)でもリセットされる(`score > best_score` で `no_improve_streak = 0`)。これは「incumbent を上回る改善が1件でも出れば無改善でない」という妥当な定義で、撤退が早まり過ぎる方向ではない。仕様(ADR 0021「連続10試行で練習スコアが改善しなければ撤退」)と矛盾しない。

#### (3-d) 過剰探索(無限試行)の経路が無いか — 合格

外側 `while True` は (i)cap 到達 (ii)patience 到達 (iii)`best_move is None`(収束・`search.py:196-198`)のいずれかで必ず break。axes 各リストは有限・1パスの内側ループも有限。無限ループ経路なし。テスト `test_F012_3_converges_before_cap_when_space_small`(`tests/test_F012_trial_cap.py:128-138`)が小空間収束(`trial_count < 50`)を固定。

**判定**: F-012-3 = **実装済**。

### 観点7: greedy の正しさ

#### (7-a) 座標上昇が練習ベスト構成を返す論理(単調改善・収束) — 合格

基準構成(各軸先頭値・`search.py:119`)から開始し、1パスで各軸×各候補値を固定順走査して「最も改善する単一変更」(`best_move` = best_move_score を厳密に更新する候補・`search.py:184-189`)を採用、改善なしで収束(`best_move is None` → break・`search.py:196-198`)。incumbent は採用 move でのみ前進し best_score は単調非減少。テスト `test_F012_2_baseline_kept_when_no_change_improves`(`tests/test_F012_practice_only.py:111-126`)が「どの変更も改善しないなら基準構成から動かない」を、`test_F012_2_picks_specific_axis_value_by_practice_score`(`tests/test_F012_practice_only.py:81-91`)が離散軸での最良値選択を固定。これは座標上昇法の正しい単調改善・収束論理。

注(局所最適の既知性質・欠陥ではない): greedy 座標上昇は大域最適を保証しない(局所最適に収束しうる)。ADR 0021 が手法を「決定的 greedy 座標上昇」と明示的に選定しており、これは仕様どおりの設計選択。test_F012_2_selects_config_with_highest_practice_score(`tests/test_F012_practice_only.py:44-66`)の scorer は単調分離可能(各軸が独立加算)なため greedy が大域最適に到達する例で、greedy が一般に大域最適を返すことを主張するものではない。仕様逸脱ではない。

#### (7-b) SelectionProvenanceRecord を dict で生成する選択が GUARD_IF 契約と整合するか — 合格

`search.py:137-142` の dict キー `{eval_id, split, scenario_id, score}` は GUARD_IF §2 `SelectionProvenanceRecord` dict 契約と完全一致。`check_selection_purity`(`src/supreme/guard.py:304-310`)が `rec.get("split")` を参照する実装と整合(キー名一致)。guard 非改修のため F-012 側で dict 生成する設計判断は GUARD_IF §2「F-012 が生成」と整合。

**判定**: 観点7 = **実装済(greedy 論理・provenance 契約とも整合)**。
