## 観点2: 観測式→HGF の解釈(実装者の判断・重点)

実装者の申告: 「ADR 0022 の『sigmoid→HGF→h_q=sigmoid(μ1)』は二重 sigmoid に読めるが、生 logit→HGF→h_q=sigmoid(μ1) を採用」。

### 2-(a) テストを通すための妥当な解釈か

**実現箇所**: `core.py:343-362`(`_quality_obs_raw_logits` = 生 logit)・`core.py:379-391`(`_hq_vol_sequences` = HGF→`sigmoid(μ1)`)

数値検証(代表値で方向性を確認):
- 高 QoS(benign QoS=0.95, latency=20): logit = −2 + 5·0.95 − 4·(20/200) + 1.5·0.5 = **+3.1** → HGF μ1 は logit スケールで観測へ追従 → `h_q = sigmoid(μ1) ≈ 0.957` → `quality.classify` で `h_q≥0.93 ∧ vol<0.01 → GOOD`(`quality.py:56`)
- 低 QoS(QoS=0.05, latency=190): logit = −2 + 5·0.05 − 4·(190/200) + 0.75 = **−4.8** → `h_q ≈ sigmoid(−4.8) ≈ 0.008 < 0.25 → BLOCK`(`quality.py:50`)

生 logit を HGF に通すと μ1 は logit スケール([−∞,+∞] 近傍)で観測へ追従するため、最終 `sigmoid(μ1)` が [0,1] の h_q を与える。これは `quality.classify` の閾値(0.25/0.55/0.93、`quality.py:50-57`)と整合する一貫した1回の squashing。**もし ADR 文面どおり sigmoid→HGF にすると、HGF 入力が既に [0,1] に潰れ μ1 も [0,1] 近傍に張り付き、`quality.classify` の 0.93 ゲートや 0.25 床に届きにくくなる**(GOOD/BLOCK の振れ幅が縮小)。よって生 logit 採用はテスト方向性(`test_Fbase001_wiring.py:215-246`)を通すための妥当かつ自然な解釈。

**判定**: 妥当。

### 2-(b) ADR 0022 と矛盾しないか

ADR 0022 決定3(行32)の字面は「`...→ sigmoid → HGF`」。実装は「生 logit → HGF → `sigmoid(μ1)`」。**字面上は squashing の位置がずれており、文面と実装に乖離がある**。ただし ADR 0022 残件(行75)に「observation 式/HGF パラメータ・証拠抽出の閾値は baseline 忠実値を出発点(δ_strong は F-013 測定)」とあり、HGF 段の正確な squashing 位置は F-013 までの調整余地として明示的に開かれている。実装の docstring(`core.py:76-80`, `343-349`, `379-385`)はこの解釈を明記している。

**判定**: 構造的な意図(高 QoS→GOOD・低 QoS→BLOCK へ単調に写す)とは矛盾しないが、**ADR 0022 決定3 の字面とは乖離する**。ADR 追記で「観測式は生 logit を HGF へ流し、出力段で h_q=sigmoid(μ1) とする(二重 squashing を避ける)」を明文化すべき(下記推奨アクション)。

### 2-(c) wiring の方向性が構造的に成立するか(過適合でないか)

- h_q は QoS の単調増加・latency の単調減少関数(`core.py:354-360` の係数 +5·qos, −4·latency)。HGF と sigmoid はいずれも単調変換。したがって **QoS↑/latency↓ → h_q↑ → GOOD 側**、**QoS↓/latency↑ → h_q↓ → BLOCK 側** が、特定のテスト入力に依らず構造的(単調性)に成立する。
- 中間 QoS でも単調に DEGRADED へ遷移する(閾値 0.55/0.93 の間)。これは入力点ではなく単調写像の性質に依存しており、過適合でない。

**判定**: 構造的に成立(単調性ベース)。特定テスト入力への過適合ではない。

## 観点3: wiring 用チューニング定数の過適合(重点)

### 3-1. 観測式係数(`core.py:82-92`)

baseline 観測式の係数(bias −2, qos +5, latency −4/200, wobs +1.5)を採用。`id_const=1.0` 固定で寄与 0、`w_obs_bar=0.5` 縮退既定。これらは QoS↑→h_q↑ の単調性を保つ符号であり、方向性は係数の絶対値でなく**符号**で決まる。一般入力(任意 QoS/latency)でも単調性が崩れない。

**判定**: 過適合でない(符号依存・単調)。

### 3-2. mode logit 係数(`core.py:102-108` / `_mode_logits` `core.py:297-328`)

mode logit は block=2.6(`mode.py:35`)を越えるよう設計:
- emergency=5.0 / alert_required=4.0(安全 mode・`mode.hysteresis` で減衰されない `mode.py:41,61-64`)→ 即発火。
- conv_ongoing=4.0 / forward_caution=4.0 / env_change=4.0(非安全・quiet 起点で block 2.6 減衰 → 4.0−2.6=1.4 > quiet 0.0)→ 持続で遷移。

block 超の余裕(1.4)は単発フレームでもヒステリシス突破するが、これは「強い証拠は遷移させる」設計意図(ADR 0015 決定2)に沿う。**会話/接近/品質劣化の各証拠が立てば必ず quiet を上回る**構造で、特定入力値ではなく「証拠 bool の有無」で方向が決まる。

**潜在的な脆さ(リスク中・指摘)**: 非安全 mode が複数同時に立つ場合(例: 接近 forward_caution=4.0 ∧ 品質劣化 env_change=4.0)、両者が同値1.4 になり、`mode.hysteresis` の argmax tie-break は「quiet と同値のときだけ quiet 優先」(`mode.py:74-76`)で、非安全 mode 同士の tie は**辞書反復順(挿入順)依存**になりうる。`_mode_logits` は dict を `logits["emergency"]→conv_ongoing→forward_caution→env_change` の固定順で構築する(`core.py:305-326`)ため、Python 3.7+ の挿入順保証により**決定的ではある**が、ラベルの優先関係が「コード上の if 順序」という暗黙仕様に依存している。F-013 の方向性評価で複数非安全 mode が競合する入力が出た場合、優先順位が ADR で明示されていないため意図とずれる余地がある。**決定性は保たれる(観点4 で再確認)が、優先順位の明文化は将来課題**。

**判定**: 主要方向性は過適合でない(証拠 bool 依存)。非安全 mode 同士の tie 優先順位は暗黙仕様(決定的だが ADR 非明記)。

### 3-3. scene 閾値(`core.py:419-429`)

`scene_mod.fit([])`(空練習)を呼ぶ(`core.py:428`)。空練習では `scene.fit` の `samples` が空 → `accuracy` が常に 0.0(`scene.py:421-423`)→ 座標降下が候補を採らず**グリッド先頭固定**(`vol_high=0.005, persist_high=0.1, level_low=0.2`、`scene.py:370-372,427-431`)。これは決定的かつ入力非依存の既定 params。

scene health 信号は `sigmoid(quality_logit)`(`core.py:409-416`)。benign で ≈0.957 > level_low 0.2 → STABLE 側、低 QoS で ≈0.008 < 0.2 → DEGRADING 側。`test_Fbase001_wiring.py:254-271` の「持続変化系列で CHANGING/DEGRADING が出る」は HGF 層2 ボラ or level_low 下抜けで満たされる。

**判定**: 過適合でない(fit([]) は決定的な既定 params 抽出として機能・level_low 0.2 と sigmoid 値域の関係で方向性が構造的)。

**コメント(設計判断の確認)**: `fit([])` を「決定的な既定 params 生成器」として流用する手法はやや非自明だが、`scene.fit` の空入力時挙動(グリッド先頭固定)を利用した決定的取得で、乱数を持ち込まない。`core.py:428` のコメントが意図を明記している。scene の learnable params(本来 F-013 で fit)を core が独自に固定している点は、ADR 0022 残件(行75「閾値は baseline 忠実値を出発点・δ_strong は F-013 測定」)の範囲内。

### 3-4. δ_strong / 結線の脆さの総括

δ_strong(強い項目の維持判定)は F-013 測定でスコープ外(正)。結線の**方向性**は (1)観測式の符号による単調性、(2)mode logit の block 超余裕、(3)証拠 bool の有無、で決まり、特定テスト入力値への依存は観測されない。脆い点は 3-2 の非安全 mode 同士の優先順位(暗黙仕様)のみ。

## 観点4: 決定性(F-基盤-001-2)

### 4-2. 非決定経路(dict 反復順/集合/浮動小数累積順)

- dict 反復: `_mode_logits` の logits dict は固定順で構築(`core.py:305-326`)。`mode.hysteresis` は dict を走査するが Python 3.7+ 挿入順保証で決定的(`mode.py:70-77`)。`run_supreme_scenarios` は `scenarios.items()` を反復(`core.py:548`)するが、出力も dict キー対応で順序非依存(各 scenario 独立)。
- 集合(set): core 本体に set 由来の順序依存ロジックは無い(view 組み立ては固定キー)。
- 浮動小数累積順: HGF/persistence は系列を**先頭から固定順**で逐次累積(`scene.py:134-164`)。core は系列順を変えず i=0..N で処理(`core.py:464`)。累積順は入力順に一意。

### 4-3. harness.check_reproduction 合格

**実現箇所**: `test_Fbase001_determinism.py:152-170` が同一入力2回 run → `harness.check_reproduction(eps_abs=1e-9, eps_rel=1e-6)` で `reproduced=True`・mismatch 空を固定。さらに `test_Fbase001_determinism.py:53-129` が「2回完全一致」「sleep 挟んでも一致」「config 指定時一致」「連続3回で状態漏れなし」を固定。

**コメント**: 呼び出し間の状態漏れ防止は `_run_one_scenario` 内のローカル初期化(`core.py:459-463`)で担保。モジュールレベルのミュータブル状態を core は持たない(定数のみ `core.py:82-112`)。

**判定**: 実装済。決定性は構造的に担保される。

## 推奨アクション

1. **[優先度: 高 / 文書のみ]** ADR 0022 決定3 に観測式の squashing 位置を追記する。現状の字面「sigmoid → HGF」(decisions/0022 行32)を、実装の「生 logit → HGF → h_q=sigmoid(μ1)(二重 squashing を避ける)」に整合させる追記を入れる。実装者の判断(申告)を ADR に固定し、図(ADR)とコードのズレを解消する。コード修正は不要。
