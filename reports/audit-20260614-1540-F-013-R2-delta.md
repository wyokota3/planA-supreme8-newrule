## 検証1: fail-closed の正しさ（開封前停止・封印不開封・枠不消費）

**検証箇所**: `src/supreme/sealeval.py:397-417`

```python
spec = harness.canonical_metric_spec()

# 0) 開封前 fail-closed 窓内不変条件検証（ADR 0023 申し送り R2）。
n_scenarios = len(scenario_ids)
last_read_ts = float(issued_ts) + max(0, n_scenarios - 1)
if not (last_read_ts < revoked_ts):
    min_revoked_ts = last_read_ts
    raise EvalWindowTooNarrow(...)

# 1) 1回だけ開封（aggregate 強制・store 自身の guard 発行）。
token = seal_store.open_eval_session(aggregate, session_id, issued_ts)
```

**判定: 機構的に成立。** 根拠（順序・副作用の追跡）:

- **検証は開封より前**: `raise EvalWindowTooNarrow`（`sealeval.py:408`）は `seal_store.open_eval_session(...)`（`sealeval.py:417`）より**前のソース行**にあり、間に開封・read・状態変更を起こす副作用は無い（`spec = harness.canonical_metric_spec()`（`sealeval.py:397`）は固定タプルからの純関数で副作用なし）。不成立時は `open_eval_session` に到達しない。
- **封印を一度も開封しない**: 開封は `open_eval_session` 単一経路（前回監査 F-013-3 で確認済み）。これに到達しないため `SearchGate.open_token_for_eval`→`SealGuard.issue_token` も呼ばれない。生涯計数加算 `self._lifetime_session_count += 1`（`guard.py:205`）は **issue_token 内**にあり、未到達ゆえ加算されない（生涯計数 0 のまま）。
- **session_state.json 不変（枠不消費の永続面）**: 永続化 `_persist_session_state()` は `open_eval_session` の発行成功後（`sealset.py:295`）にのみ呼ばれる。未到達ゆえ session_state.json は進まない。テスト `test_F013_eval_window.py:151-168`（`..._does_not_persist_session_state`）が**別インスタンス（同一 root_dir）**で `lifetime_session_count()==0` を固定し、永続面でも枠を焼いていないことをプロセス跨ぎで担保する（GUARD_IF §3 運用規約2）。
- **read も発生しない**: read ループ（`sealeval.py:423-425`）も検証より後段ゆえ未到達。access_log への記録も無い。
- **テストの裏付け**: `test_F013_eval_window.py:135-148`（`..._does_not_consume_quota`）が同一 store インスタンスで `lifetime_session_count()==0` を固定。`test_F013_eval_window.py:98-111` が `EvalWindowTooNarrow` が公開かつ `Exception` サブクラスであることを固定。

**機構穴の確認**: 検証式 `last_read_ts < revoked_ts` の評価で例外が起きうるか? `float(issued_ts)` と `revoked_ts` の比較。`issued_ts`/`revoked_ts` は契約上 float（GUARD_IF 運用規約4・呼び出し側供給）。型不正は本検証より前ではなく後段の guard/sealset で弾かれる設計だが、本検証は数値比較のみで開封副作用を持たないため、たとえ後段で型エラーが出ても**開封前**であり枠は焼かれない（fail-closed の向きは保たれる）。

**結論**: fail-closed は正しい。不成立時に封印を一度も開けず、生涯計数 0・session_state.json 不変（枠不消費）で停止する。

## 検証2: 不変条件の式の正しさ（厳密 `<`・N=1・境界・窓ゼロ）

**検証箇所**: `src/supreme/sealeval.py:404-406` ＋ read ts 割当 `sealeval.py:422-425`

read ts 割当（不変・無改変）:
```python
read_ts = float(issued_ts)
for sid in scenario_ids:
    sealed_gt = seal_store.read_sealed_gt(sid, token=token, ts=read_ts)
    read_ts += 1.0
```
→ scenario の k 番目（0-indexed）read の ts = `issued_ts + k`。N=len(scenario_ids) のとき **last read ts = issued_ts + (N-1)**。

検証式:
```python
last_read_ts = float(issued_ts) + max(0, n_scenarios - 1)
if not (last_read_ts < revoked_ts):
    raise EvalWindowTooNarrow(...)
```

**判定: 式は正しい。** 半開区間 [issued_ts, revoked_ts) との整合を1点ずつ確認:

- **窓の半開性の根拠**: `guard._within_token_window`（`guard.py:238-248`）は `ts >= token.revoked_ts` を窓外（`guard.py:246-247`）とし、下端は `ts < issued_ts` のみ窓外（`guard.py:244-245`）。すなわち `ts == revoked_ts` は**窓外**、`ts == issued_ts` は窓内。これは ADR 0008 決定3・コメント `guard.py:241` と一致。**audit_seal_access が read の窓内性を最終判定する経路**は `_within_token_window`（`guard.py:271`）。
- **全 read が窓内 ⇔ last read ts が窓内**: read ts は `issued_ts` から +1 で狭義単調増加。最小 read ts = `issued_ts`(≥ issued_ts ＝窓内側下端)、最大 = `issued_ts+(N-1)`。全 read が `[issued_ts, revoked_ts)` 内 ⇔ 最大 read ts < revoked_ts ⇔ **`issued_ts + (N-1) < revoked_ts`**。式の右辺は厳密 `<` で、半開区間の上端開（`==revoked_ts` は窓外）を正しく反映する。
- **N=1**: `max(0, 1-1)=0` → last_read_ts = issued_ts。条件は `issued_ts < revoked_ts`。窓が空でなければ成立、窓ゼロ（issued_ts==revoked_ts）なら不成立。テスト `test_F013_eval_window.py:208-218`（窓ゼロ→raise）と `:221-233`（issued_ts=100.0/revoked_ts=100.5→完走）が両側を固定。式は正しい。
- **N=0 の防御**: `max(0, n_scenarios-1)` の `max(0, ...)` は N=0 のとき `-1` を `0` に丸め、last_read_ts=issued_ts。負ぶれによる誤って広すぎる判定を防ぐ（過剰停止も過剰通過もしない）。本テストに N=0 ケースは無いが、式自体は安全側。
- **境界（last read ts == revoked_ts は窓外）**: テスト `test_F013_eval_window.py:190-201` が N=2・issued_ts=100.0・revoked_ts=101.0 → last_read_ts=101.0 → `not (101.0 < 101.0)` → raise を固定。半開上端の開を厳密 `<` で正しく扱う。
- **境界（ぎりぎり成立は通す）**: テスト `test_F013_eval_window.py:175-187` が revoked_ts=101.5 → last_read_ts=101.0 → `101.0 < 101.5` True → 完走・生涯開封数=1 を固定。fail-closed が genuine に成立する構成を**過剰停止しない**ことを担保（誤検出の不在）。

**FP 観点の確認（テスト緑で出ない穴）**: `issued_ts + (N-1)` の加算は整数値の float 加算（`100.0 + 1` 等）で、本テスト構成の値域（小数1桁・小整数オフセット）では FP 誤差が生じない（`100.0+1.0==101.0` は厳密）。一般には `revoked_ts` が `last_read_ts` に FP 誤差幅で接近する病的構成で `<` の判定がブレうるが、(a) この比較は read 窓判定 `_within_token_window` の `>=` と**同じ float 比較規約**で一貫しており、検証が通れば実 read も同規約で窓内になる（検証と実挙動が同じ演算で整合）、(b) verdict 境界の ε とは目的が異なる（こちらは ts 窓で ε 吸収は不要かつ不適切）。よって ε を入れない素朴な `<` が正しい。**式に ε を足していないことはむしろ正しい**（窓 ts は研究者供給の意図値で、FP 境界吸収を入れると半開区間の一意性を崩す）。

**結論**: 不変条件式 `issued_ts + max(0, N-1) < revoked_ts`（厳密 `<`）は半開区間 [issued_ts, revoked_ts) と完全整合。N=1・境界・窓ゼロをすべて正しく扱う。

## 検証5: R2 のクローズ可否（＋機構的補正）

**判定: R2 はクローズ可。**

R2 の本質的懸念＝「窓内不変条件を**開封前に検証する機構が無く**、窓が狭い/scenario が多い本番構成で**開封枠を焼いた後に**評価が壊れる」は、本対処で解消した:
- 開封前検証が `open_eval_session` より前に置かれ（検証1）、不成立時に枠を焼かず停止する。
- 式が半開区間と整合し、境界・N=1・窓ゼロを正しく扱う（検証2）。
- 既存正常系を壊さず（検証3）、最小対処（検証4）。

### 重要な機構的補正（前回 R2 の障害像の修正・判定は変えない）

前回監査 R2 は障害像を「`read_sealed_gt` が **AccessDenied** を送出し run_sealed_evaluation が**途中で例外終了**する」（`audit-...1526...:218`）と記述したが、実コードの read/revoke 順序では**この障害像は部分的に不正確**:

- read（`sealeval.py:423-425`）は revoke（`sealeval.py:456`）**より前**に走る。read 時点で `token.revoked_ts is None`（`open_eval_session`→`issue_token` は `revoked_ts=None` でトークン生成・`guard.py:204`）。
- read のゲートは `seal_store.read_sealed_gt`→`self._guard.is_access_allowed(token, ts)`（`sealset.py:316`）。この `SealGuard.is_access_allowed`（`guard.py:220-231`）は **`active`（revoked_ts is None）かつ `ts >= issued_ts`** のみを見て、**上端窓は見ない**（`guard.py:231` は `return ts >= token.issued_ts`）。
- ゆえに read 時点（未失効）では `read_ts >= revoked_ts` でも `is_access_allowed` は **True を返し read は成功する**。窓外化は read を止めない。
- 窓外性が顕在化するのは最後の `guard.audit_seal_access(...)`（`sealeval.py:459`）。ここは revoke 済みトークンに対し `_within_token_window`（半開・`guard.py:271`）で各 read を突合するため、`read_ts >= revoked_ts` の read があると **audit_passed=False** になる。

→ つまり実際の障害は「**read 中断**」ではなく「**read は完走するが、開封枠を焼いた上で audit が不合格**になる」。これは前回 R2 が想定したより**むしろ悪い**（壊れていることに気づきにくく、貴重な生涯1回の開封枠を消費済み）。本対処の fail-closed 検証は**この実際の障害も同時に防ぐ**（開封前に止めるので audit 不合格にも枠消費にも至らない）。よって対処の妥当性・必要性はむしろ補強され、R2 はクローズ可。

**ただし文書整合の推奨（コード修正不要・低リスク）**: ADR 0023 申し送り R2 の本文（`decisions/0023-...md:99-104`）と新規テスト docstring（`test_F013_eval_window.py:10-11`「窓外 read で AccessDenied 中断しうる」）・実装コメント（`sealeval.py:51` は「開封後の窓外 read で送出される AccessDenied とは別物」と正しく書くが、`test_F013_eval_window.py:11/123` は「AccessDenied 中断」を障害像として記述）は、上記の read/revoke 順序を踏まえると「実際は audit 不合格（枠消費後）が主たる帰結」と補足すべき。**この補正は R2 のクローズや対処の正しさを変えない**（fail-closed 検証はどちらの帰結も防ぐ）。R3a として記録する。

### 受け入れ条件への影響

- **F-013-3（封印開封が単一の開封セッション・生涯1回）**: 本対処で**保全が強化**された。窓不整合の構成で「開封枠を焼いた上で audit 不合格/評価破綻」に陥る経路を、開封前に型付き例外で遮断する。生涯1回の貴重な開封枠を、窓設定ミスから機構的に守る。前回監査の F-013-3 判定（実装済）は維持・強化。
- F-013-1/2/4: 影響なし（検証は成立時に素通りゆえ採点・verdict・依存結線に変更なし）。
