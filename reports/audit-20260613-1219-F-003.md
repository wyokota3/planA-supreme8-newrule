## 着手条件（ADR 0010 決定4 / G1・D1）の解消判定 — 最重点

### G1（逆方向交差）: 新規 train root ∩ 封印 root = ∅ の検査が augment 登録経路にあるか

**実現箇所**: `src/supreme/augment.py:142-150`
```python
        sealed_roots = self._seal_store.sealed_lineage_set()
        if parent_root in sealed_roots:
            raise SealCrossError(
                f"増強 train の root {parent_root!r} が封印 root と交差する"
                f"（train→seal 方向の逆方向交差・着手条件 G1）。何も登録しない。"
            )
```
- **検査の存在**: 増強登録の前に「新規 train の root（`parent_root`）∈ 封印 root 集合」を検査し、交差時は `SealCrossError`（`augment.py:52-57`・`datagov.LineageCrossError` を継承）で**何も登録せず**拒否する。検査は生成・登録（`:161-184`）より**前**に位置する（順序正しい・後述）。
- **封印 root の都度取得（構築時固定キャプチャでない）**: `sealed_roots = self._seal_store.sealed_lineage_set()`（`:145`）は **`augment` メソッド内で呼び出しのたびに**実行される。`__init__`（`:104-109`）は `seal_store` 参照のみ保持し、root 集合をキャプチャしない。継続検証点として正しい。
- **F-002 との対向**: F-002 は封印登録時に「封印 record root ∩ train root = ∅」を検査（`sealset.py:153-161`・`reports/audit-20260612-2238-F-002.md` の F-002-1）。F-003 は train 追加時に「train root ∩ 封印 root = ∅」を検査。**両方向が閉じている**（封印→train 方向は F-002、train→封印 方向は F-003）。

**テスト**: `tests/test_F003_seal_cross.py` — 非交差で登録成功（陽性対照）`:79-98`、**親 root 自体が封印済みの直接交差拒否** `:105-122`、**孫経由交差を root へ畳んで拒否** `:129-148`、専用例外公開 `:151-162`、**封印集合の都度取得（後から1件増えた封印を増強時点で検出）** `:209-243`。`:209-243` が「構築時固定キャプチャでない」ことを明示的に固定する（封印 C のうちは A 増強が通り、root B を後から封印追加後に B 増強が拒否される）。

**判定**: **G1 解消**。検査の存在・都度取得・F-002 との対向の三点が実装とテストで固定。ADR 0010 決定4 の「逆方向交差の検査統合点を設計に含めること」を満たす。ADR 0010 推奨案（datagov 単一権威化）は ADR 0011 決定3 で不採用とし、F-003 側突合で代替する設計判断は明文化済み（blast radius 最小化）。

## 抜け穴・退行・順序の探索

### 1. `_get_parent_record` の payout split 跨ぎ探索と `LineageCrossError` 握り潰し（実装者自己申告の懸念）

**該当**: `src/supreme/augment.py:188-209`
```python
    def _get_parent_record(self, parent_id):
        for split in ("train", "seal", "unassigned"):
            try:
                records = self._governor.payout(split)
            except datagov.LineageCrossError:
                continue
            for rec in records:
                if rec["meta"]["scenario_id"] == parent_id:
                    return rec
        raise ParentNotRegisteredError(
            f"親 {parent_id!r} の登録レコードを取得できない"
        )
```

**(a) 親取得の正しさへの影響**: `_get_parent_record` は生成器に渡す親レコードを取得するためだけに使う（`:140`）。`payout(split)`（`datagov.py:589-602`）は seal∩train 交差時に `LineageCrossError` を送出する防御を持つが、ここでの探索目的では交差している split があっても**他 split を探せばよい**ため `continue` で握り潰す。親は `resolve_root`（`:133`）が成功している＝登録済みなので、いずれかの split に必ず存在する。**親取得の正しさは損なわれない**（探索の網羅性は train/seal/unassigned の3 split で全状態を覆う）。最後の `raise ParentNotRegisteredError`（`:207`）は「resolve_root は通るが payout に現れない」論理的に到達しないはずの経路の安全側フォールバック（docstring `:205-206` が明記）。

**(b) 封印交差検出を弱めないか**: **弱めない**。封印突合（G1・`:142-150`）は `_get_parent_record`（`:140`）より**前**に既に評価される順序ではない点に注意が必要。実際のコード順序は `:133`（resolve_root）→ `:139`（generation_of）→ `:140`（`_get_parent_record`）→ `:145`（封印突合）。すなわち `_get_parent_record` は**封印突合より先に走る**。しかし `_get_parent_record` は親レコードを取得して返すだけで**何も登録・改変しない**（read-only 探索）。封印突合が交差を検出すれば `:147` の `SealCrossError` で何も登録せず終了する。`_get_parent_record` が seal split を含めて探索することは、親が seal にいる（=封印 root の素材）ケースでも親レコードを取得できることを意味するが、その場合は直後の封印突合（`:146` `parent_root in sealed_roots`）が交差を検出して拒否する。よって**親取得が封印突合より先に走っても、登録副作用が無いため誤った挙動にはならない**（取得しても、交差なら登録に至らない）。

**(c) 例外握り潰しが他のエラーを隠さないか**: `except datagov.LineageCrossError` は `LineageCrossError` のみを捕捉する（`datagov.LineageError`・`ValidationError`・その他は捕捉しない）。`payout` が送出しうる例外は構造上 `LineageCrossError` のみ（`datagov.py:589-602`）。よって**他のエラー型を隠す経路は無い**。ただし `LineageCrossError` を握り潰すことで「seal と train が現に交差している governor 状態」を `_get_parent_record` は素通りするが、これは F-003 の責務（train 追加の単一窓口）の外の既存交差であり、F-003 の封印突合（`:146`）は親の root が**封印 root 集合**（seal_store 由来）と交差するかを見るので、governor 内部の seal/train 交差状態とは独立に正しく機能する。

**判定**: `_get_parent_record` の握り潰しは (a)(b)(c) いずれも穴を作らない。**read-only 探索＋登録副作用なし＋単一例外型のみ捕捉**が成立理由。ただし**この経路はテストで直接固定されていない**（後述カバレッジ）。

### 2. 封印突合・gt_origin 検算・親系統確定・登録の順序

実コードの順序（`augment.py:131-184`）:
1. `:133` 親 root 再解決（未登録なら `ParentNotRegisteredError`）
2. `:139` 親 generation 取得
3. `:140` 親レコード取得（read-only）
4. `:145-150` **封印突合（G1/D1）** — 交差なら `SealCrossError` で**何も登録せず終了**
5. `:153-156` gt_origin 検算 — drop なら**何も登録せず空リスト返却**
6. `:161-183` count 件の生成 → `_finalize_lineage` → `register` → `AugmentResult`

**穴の評価**:
- **登録が突合より先に走る経路は無い**: `register`（`:173`）は封印突合（`:146`）と gt_origin 検算（`:154`）の**両方を通過した後**のループ内でのみ呼ばれる。封印突合・検算は登録の前。
- **drop された派生が副作用を残す経路は無い**: drop は `:154-156` で `count` 件生成ループに入る**前**に `return []` する。生成も登録も発生しない。**部分的副作用なし**。
- **flag された派生**: `:163-183` のループで生成・登録される（`unverified_gt=True` 付き）。これは意図された挙動（SPEC 異常系「フラグ」側）。
- **封印突合が drop 検算より先**: 封印交差は drop/flag に関わらず最優先で拒否される（リーク防止が gt 検算より厳格）。妥当な順序。
- **count 件のうち一部だけ register が失敗する場合**: `register`（`:173`・`datagov.register`）が `ValidationError`/`LineageError` を送出すると、ループ途中で例外伝播し、**それまでに register 済みの派生は governor に残る**（部分登録）。ただし生成器は `_fake_generator` 系で決定的に妥当なレコードを返す前提（テスト構成）であり、本物生成器が途中で不正レコードを返す場合の部分登録の原子性は**機構として保証されていない**。これは U17/実データ投入時の生成器品質の問題に隣接する既知の機構限界（テスト対象外・本物生成品質はスコープ外＝ADR 0011 決定1）。

**判定**: 順序に致命的な穴は無い。封印突合 → gt 検算 → 親系統確定 → 登録 の順は正しい。drop の部分副作用なし。唯一の機構限界は「count 件登録の途中失敗時の部分登録の非原子性」だが、これは本物生成器品質（U17 隣接・スコープ外）の問題であり、テストが要求していない領域。

### 3. gt_origin 検算が「文字列一致のみ」であることの限界

`unverified = (gt_origin == self.generator_lineage)`（`:153`）は `gt_origin` 文字列が `generator_lineage` 文字列と異なれば「別系統で確定済み」とみなす。**`gt_origin` の値が真に別系統手段で確定された保証は無い**（呼び出し側が任意文字列を渡せる）。この限界は:
- モジュール docstring `augment.py:13-14`（「具体的な U17 ワークフローは実データ投入時まで保留」）に明記。
- ADR 0011 決定1（`decisions/0011-f003-augment-policies.md:21`）と申し送り `:45`（「U17 の具体ワークフローは実データ投入時の課題として残置」）に明記。
- TEST_STRATEGY 穴5（`specs/TEST_STRATEGY.md:118`・GT の正しさはテスト外）が上位限界として記録。

**判定**: 限界は **U17 申し送りとして明記済み**。機構のみ実装のスコープ内であり「正」。

### 4. 退行（既存機能への影響）

`augment.py` は `datagov`/`sealset`/`guard` を改修しない（決定3 遵守・前述）。`__init__.py` への追加は import 1行と `__all__` 登録のみ。**既存 F-001/F-002/F-014 の挙動への影響経路は無い**（テスト 288件全パスが独立確認済みであり、262→288 の +26 が F-003 の新規分）。
