# 意図と違うものができたときの修正フロー

Claude Code に実装させたものが意図と異なる結果になったとき、どう対処するか。
**規模を見極めて、適切な対応を選ぶ**ことが最重要。

「全部直して」と指示すると、汚れたコンテキストの上に汚れた修正が積み重なり、悪化する。
逆に「小さな問題」を大規模な仕切り直しで対応すると、無駄な時間を消費する。

## 4つの規模

### 規模A: 一つの受け入れ条件が満たされていない (約60%のケース)
監査レポートで「未実装」と判定された項目があるなど、明確に1点が問題。

### 規模B: 一機能の解釈がそもそもズレていた (約25%のケース)
監査では「実装済」になっているが、人間が見ると意図とは違う動き方をしている。
仕様の解釈段階でズレている。

### 規模C: 全体設計がズレていた (約10%のケース)
複数機能にわたって、想定と違うアーキテクチャになっている。
コンテキストが既に汚染されている。

### 規模D: SPEC.md が間違っていた (約5%のケース)
実装と意図のズレではなく、仕様自体が間違っていた、または不十分だった。

---

## 規模A: 一つの受け入れ条件が満たされていない

### 兆候
- `/audit F-XXX` のレポートに「未実装」項目がある
- 「F-XXX-3 の境界条件のテストが失敗している」のような局所的な失敗
- 「ボタンの位置が違う」「エラーメッセージが想定と違う」など、明らかに一点

### 対処の流れ

1. **監査レポートを根拠として明示する**

```
./reports/audit-20260520-1430-F-001.md の指摘に従って、
F-001-3「金額0円の扱い」を実装してほしい。
implementer を呼んで、該当箇所だけを修正させて。
テストは変更しないこと。
```

ポイント:
- 監査レポートのファイル名を明示する
- どの受け入れ条件 (F-001-3) かを明示する
- 「テストは変更しないこと」を念押し

2. **修正後、再監査する**

```
/audit F-001
```

修正が反映され、新しい監査レポートで「実装済」になることを確認。

3. **git commit**

```
WORKFLOW.md のコミット規約に従って、commit して。
メッセージは [F-001] fix: 金額0円時の扱いを修正
```

### やってはいけないこと

❌ 「F-001 を全部見直して」(範囲が広すぎる)
❌ 「テストを通すように調整して」(テスト改変の口実になる)
❌ 監査レポートを参照せずに直接「ここを直して」(根拠が記録に残らない)

---

## 規模B: 一機能の解釈がそもそもズレていた

### 兆候
- 監査では「実装済」だが、実際に動かしてみると意図と違う
- 仕様書を読み返すと、自分が想定していた解釈と違う書き方になっている
- 「ここは○○のつもりだったが、××に解釈されている」

### 対処の流れ

1. **まず実装を止める**

```
F-001 の実装解釈が私の意図と異なる。
まだ追加の作業はしないで。一旦停止して、状況を整理したい。
```

2. **git で該当機能の開始時点まで revert する**

```
F-001 の実装は git で revert したい。
git log で F-001 の最初のコミットを特定して、その直前まで戻すコマンドを提示して。
私が承認してから実行する。
```

戻すコマンドの例(参考):
```bash
git log --oneline | grep F-001  # F-001関連のコミットを特定
git revert <最初のF-001コミットのhash>..HEAD  # それ以降を全部revert
```

3. **SPEC.md の該当機能を見直す**

```
SPEC.md の F-001 を私と一緒に見直したい。
spec-reviewer を呼んで、F-001 の節だけに絞った曖昧さチェックをして。
特に、解釈の余地がある表現を全て指摘して。
```

4. **必要に応じて外部チャットで仕様を修正**

spec-reviewer の指摘が多ければ、外部チャットで `.prompts/spec_update.md` を使って
SPEC.md を改訂する。

軽微な修正で済むなら、Claude Code 内で SPEC.md を直接編集してもよい。

5. **新しい SPEC.md で再実装**

```
SPEC.md の F-001 が更新された。/start-feature F-001 で実装をやり直す。
```

### やってはいけないこと

❌ 「実装はそのまま、解釈だけ変えて」(矛盾した状態が残る)
❌ revert せずに上書き修正(コミット履歴が汚れて後で追えなくなる)
❌ SPEC.md を更新せずに「コードだけ直して」(同じ問題が次回も起きる)

---

## 規模C: 全体設計がズレていた

### 兆候
- 複数の機能 (F-001, F-002, F-003) が、想定と違う構造になっている
- 「コンポーネント分割が想定と違う」「データの流れが違う」など、アーキテクチャレベルの問題
- 直前の修正指示でも改善しない、むしろ悪化する

### 対処の流れ

これは怖いケース。**新規セッションで仕切り直す**のが鉄則。

1. **現セッションでサマリを作成**

```
ここまでの作業をサマリとして ./reports/session-summary-YYYYMMDD-stuck.md に保存して。
含めるべき内容:
- 完了したと思っていた機能のリスト
- 各機能で実装したアプローチの要約
- 「想定と違う」と感じている点の具体的な箇所
- 関連するファイル一覧
```

2. **Claude Code を終了**

```bash
# /exit または Ctrl+C で終了
```

3. **新規セッションを立ち上げ**

```bash
claude
```

4. **最初の指示で状況を再構築**

```
./reports/session-summary-YYYYMMDD-stuck.md を読み込んで。
さらに ./specs/SPEC.md と ./WORKFLOW.md も読んで。

その上で、現状のコードと SPEC.md の意図のズレを分析してほしい。
auditor を呼んで、全機能 (F-001 〜 完了済み全て) を一括で監査して、
特に「実装はあるが意図と違う」と疑わしい箇所を抽出して。

修正方針はまだ提案しなくていい。まず現状把握だけして報告して。
```

5. **状況把握後、外部チャットで仕切り直しを検討**

ここで多くの場合、SPEC.md 自体に問題があったことが判明する。
外部チャットの新規セッションで `.prompts/spec_update.md` を使って、
ゼロベースで仕様を見直す。

6. **ADR を書く**

```
今回の仕切り直しの判断を ./decisions/ に ADR として記録して。
含めるべき内容:
- 何が問題だったか
- なぜ気付くのが遅れたか
- 今後同じ問題を避けるための予防策
```

### やってはいけないこと

❌ 同じセッションで「全部修正して」と指示(汚れたコンテキストでの修正は更に悪化)
❌ 監査せずに「一括で書き直して」(問題の所在が分からないまま破壊する)
❌ ADR を書かない(同じ失敗を繰り返す)

---

## 規模D: SPEC.md が間違っていた

### 兆候
- 実装は SPEC.md 通りだが、SPEC.md 自体が現実と合っていない
- 「仕様通り作ったが、これは使えない」
- 外部要因の変化(法規制、依存サービスの仕様変更など)

### 対処の流れ

これは「修正」というより「設計のやり直し」。

1. **外部チャットの新規セッションで `.prompts/spec_update.md` を使う**

2. **影響範囲を網羅的に洗い出す**

spec_update.md のプロンプトに従って、変更が及ぼす影響を全機能について分析する。

3. **新 SPEC.md と引き継ぎ指示書を得る**

4. **Claude Code で反映**

```
SPEC.md を新しい内容に更新した。
影響を受ける機能 F-001, F-003, F-007 について、
それぞれ /audit を実行して現状とのズレを把握して。
その後、必要なら /start-feature で WORKFLOW を再実行する。
```

5. **ADR は必ず書く**

```
SPEC.md の変更理由と影響範囲を ./decisions/ に詳細なADRとして記録して。
変更前後の SPEC.md の diff も別途保存。
```

---

## 修正指示の3原則(再掲)

どの規模でも共通する原則。

### 1. 根拠を渡す
「直して」と言わない。
「監査レポートのこの指摘を」「SPEC.md の F-001-3 を」「ADR 判断2 と矛盾するから」のように、
**根拠ファイルを指定**する。

### 2. 規模を見極める
- 監査レポートで指摘されているか? → 規模A
- 複数機能に波及するか? → 規模C
- SPEC.md 自体に問題があるか? → 規模D
- それ以外で、一機能の解釈ズレ? → 規模B

### 3. 修正もワークフローに乗せる
直接 implementer に「直して」と言わない。
必ずオーケストレーター経由で。
修正完了後は再度 auditor を呼んで再監査する。

---

## 修正がうまくいかない時の更なる対処

### サブエージェントが言うことを聞かない

```
ここまで <サブエージェント名> に2回修正を指示したが、毎回同じ問題が再発する。
.claude/agents/<該当エージェント>.md の定義を読み返し、
ルールが守られていない理由を分析して。
必要なら定義の改善案を提案して。
```

これでサブエージェント定義のバグが見つかることがある。
改善案が妥当ならテンプレート側にも還流する。

### 何度試しても通らない

```
F-001 の実装で3回試したが全て失敗している。
試したアプローチと失敗理由を整理して。
SPEC.md の F-001 の要件自体が技術的に実現困難な可能性も含めて議論したい。
```

「仕様が実現不可能」というケースも実際にある。
無理に実装させ続けず、仕様の見直しに戻る判断も必要。

### コンテキストが汚れた感じがする

新規セッションに切り替える(規模Cの手順を流用)。
「感じがする」レベルで切り替えてよい。コンテキスト汚染は静かに進行する。

---

## まとめ: 修正フローのチートシート

| 兆候 | 規模 | 対処 |
| --- | --- | --- |
| 監査で「未実装」が1〜2点 | A | 監査レポートを根拠に implementer を呼ぶ |
| 監査では「実装済」だが動きが意図と違う | B | git revert → SPEC.md 見直し → 再実装 |
| 複数機能で構造が想定と違う | C | 新規セッションで仕切り直し |
| SPEC.md 自体が現実と合わない | D | 外部チャットで spec_update.md |
| サブエージェントが言うことを聞かない | - | エージェント定義を見直す |
| 3回試して通らない | - | 仕様の実現可能性を再検討 |
| なんとなくおかしい | - | 新規セッションに切り替え |
