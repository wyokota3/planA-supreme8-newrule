# Claude Code でのチャット指示パターン集

このテンプレートでは、Claude Code のチャットに**長いプロンプトを毎回貼り付けない**のが基本。
プロンプトは slash command や CLAUDE.md として配置済み。
チャットでは短いトリガーを打つだけで動く。

このファイルでは、典型的な場面ごとに「何を打てば良いか」をまとめる。

## 基本原則: なぜ短い指示で済むのか

- `CLAUDE.md` は毎セッション自動で読まれる → 全体ルールは常時有効
- `.claude/commands/*.md` がslash commandとして登録済み → `/start-feature` で起動
- `.claude/agents/*.md` がサブエージェントとして登録済み → 必要時に呼べる
- `./specs/SPEC.md` と `./WORKFLOW.md` を CLAUDE.md が指示済み → 自動的に参照される

つまり、**仕組みに従ったプロジェクト構造があれば、チャット入力は最小限で済む**。
これがハーネスエンジニアリングの核心。

## セッション開始時

### 新規セッションを開いて、初回作業を始める

最初に投げる指示の例:

```
SPEC.md と TEST_STRATEGY.md と WORKFLOW.md を読み込んで、
現在のプロジェクト状況を把握してから、次に何をすべきか提案してください。
```

これで Claude Code は仕様書を読み、未着手の機能、進行中の機能、完了済みの機能を整理して報告してくれる。

### 機能Aの実装を始めたい

```
/start-feature F-001
```

これだけ。`.claude/commands/start-feature.md` が起動する。

### 仕様の曖昧さチェックだけしたい

```
/spec-review
```

`spec-reviewer` サブエージェントが SPEC.md をレビューしてくれる。

### 特定の機能を監査したい

```
/audit F-001
```

`auditor` サブエージェントが該当機能だけを監査してレポートを出す。

## 実装ループ中の典型パターン

### サブエージェントの結果に納得した

```
OK、次のステップに進んで。
```

シンプルに承認する。WORKFLOW のステップが次に進む。

### サブエージェントの結果に納得しない

#### test-writer の出力が物足りない場合

```
F-001-3 の境界条件のテストが薄い気がする。
test-writer を再度呼んで、空入力・最大値・並行実行のテストを追加させて。
TEST_STRATEGY.md の F-001 セクションも参照すること。
```

ポイント: **何が足りないか具体的に指摘する**。「もっと丁寧に」だけだと改善されない。

#### implementer の実装が意図と違う

```
implementer が書いた src/foo.py の handle_xxx 関数、
仕様 F-001-2 の「ユーザーIDが nil の場合はエラーを返す」と異なる挙動になっている。
nil チェックが入っていない。
implementer を再度呼び、F-001-2 の要件を満たすよう修正させて。テストは変更不可。
```

ポイント: **どのファイルのどの箇所が、仕様のどの項目と矛盾しているか**を指摘する。
詳しくは `FIXING_DEVIATIONS.md` を参照。

#### auditor のレポートが甘い

```
auditor のレポートで F-001-4 が「実装済」となっているが、
src/foo.py:120 を確認すると、エラーハンドリングが書かれていない。
auditor を再度呼んで、特にエラーハンドリングの実装状況を厳しく見て。
```

### サブエージェントを呼ぶ前に確認したい

明示的に「呼ぶ前に教えて」と言う:

```
次に test-writer を呼ぶ前に、どんな指示を渡すつもりか提示して。
私が承認してから呼んでほしい。
```

これは CLAUDE.md にも書かれているが、慣れていないとオーケストレーターが
独断でサブエージェントを呼ぶことがあるので、明示的に念押しすると安全。

## 議論モード(実装を止めて相談したい)

### 仕様の解釈で迷ったとき

```
F-002 の「ユーザーは複数のタグを設定できる」について、
タグの上限数、重複の扱い、空文字の扱いが SPEC.md に書かれていない。
これは私と相談すべき項目だと思う。実装は一旦止めて、3つの論点を整理して。
```

### 設計判断が必要なとき

```
F-003 の実装に入る前に、Repository パターンを使うかどうか議論したい。
SPEC.md と現状のコードベースを踏まえて、選択肢とトレードオフを整理して。
コードはまだ書かないで。
```

ポイント: **「コードはまだ書かないで」を明示する**。これがないと、議論しているつもりが実装が始まることがある。

## 振り返りとドキュメント化

### 機能完了後、ADRを書きたい

```
F-001 の実装中に「キャッシュ層を導入する」という判断をした。
これを ./decisions/ に ADR として記録して。
形式は ./decisions/ の既存ファイルに倣う(なければ標準的なADRフォーマットで)。
```

### 進捗サマリが欲しい

```
これまで完了した機能、進行中の機能、未着手の機能を一覧で。
各機能の監査レポートの場所と、未解決の懸念点も併記して。
```

### 自分が何をしたか思い出せない(数日後の再開時)

```
./reports/ の最新の監査レポートを読んで、現在の進捗状況を要約して。
直前のコミット履歴(git log -10)も参照して、次にやるべきことを提案して。
```

## セッションの切り替え

### 長くなったセッションを終わらせて新規セッションに移りたい

公式ベストプラクティスでは、コンテキストが汚れたら新規セッションに切り替えるのが推奨。

切り替え前に:

```
ここまでの作業を要約して、./reports/session-summary-YYYYMMDD.md に保存して。
新しいセッションで作業を継続するときに必要な情報を全て含めること:
- 完了した作業
- 進行中で未完了の作業
- 残課題
- 注意すべき設計判断
```

その後、Claude Code を一度終了し、新しいセッションを起動。最初に:

```
./reports/session-summary-YYYYMMDD.md を読み込んでから、
作業を再開してください。
```

これでコンテキストをクリーンに保ちつつ、必要な情報は引き継げる。

## やってはいけない指示

### 「全部やっといて」系

```
❌ F-001 から F-010 まで全部実装して。あとで確認するから。
```

これは絶対にやらない。WORKFLOW.md の意味がなくなる。
人間の承認チェックポイントを飛ばす指示は、後で必ず後悔する。

### 「テスト無視して」系

```
❌ テストが面倒だから、テストなしで実装だけ進めて。
❌ テストが落ちてるけど、無視して次に進んで。
```

役割分離型開発の最大の防御線がテストの独立性。これを崩すと全体の品質保証が崩壊する。

### 「サブエージェント使わずに直接やって」系

```
❌ サブエージェント使うの面倒だから、メインセッションで実装して。
```

これは「オーケストレーターはコードを書かない」という規律を破る指示。
コンテキストが汚れる + 役割分離が崩れる、の二重で悪い。

### 「ADRは省略して」系

```
❌ ADR書くの面倒だから省略して。
```

ADR は「なぜそうなっているか」を後で説明するための唯一の証拠。
省略すると、数ヶ月後に自分が苦しむ。

## チートシート

| やりたいこと | 入力 |
| --- | --- |
| プロジェクト状況を把握 | 「SPEC.md と WORKFLOW.md を読んで状況を把握、次にやることを提案」 |
| 機能の実装開始 | `/start-feature F-XXX` |
| 仕様の曖昧さチェック | `/spec-review` |
| 単独監査 | `/audit F-XXX` |
| 環境構築(初回のみ) | `/setup-env` |
| 進捗を絵で見る | `/dashboard` → `start dashboard.html` |
| プラン別モデル設定 | `/set-plan <pro\|max5\|max20>` |
| 利用制限到達を記録 | `/log-limit` |
| エフォートレポート生成 | `/report-effort` |
| サブエージェントの結果に納得 | 「OK、次のステップに進んで」 |
| サブエージェントに修正させる | 「<どのファイルの><どの箇所>が<仕様のどの項目>と矛盾している。再度呼んで修正させて」 |
| 議論モードに入る | 「コードは書かずに議論したい。<論点>について整理して」 |
| ADR記録 | 「<内容>を ./decisions/ に ADR として記録して」 |
| セッション要約 | 「ここまでの作業を ./reports/ に要約して」 |
| セッション再開 | 「./reports/<最新の要約> を読んで再開」 |
