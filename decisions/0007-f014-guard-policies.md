# ADR 0007: F-014(ガードレール)の実装方針 — fail-closed ①・機構のみ④・契約のテスト駆動定義

- 日付: 2026-06-12
- ステータス: 採用
- 関連: `specs/SPEC.md`(F-014/U24/U18)、ADR 0002(開封トークン)、F-014 ステップ1

## 背景

F-014 着手時点で U24(パラメータ数の定義・係数 k)と U18(探索試行回数上限)が未確定。
SPEC は「U24 確定まで F-014-1 の検査実装はブロック」とするが、F-004 で確立した
「未供給なら停止する」パターンの適用をユーザーに確認し、以下を承認された。

## 決定(ユーザー承認済み・2026-06-12)

1. **F-014-1(ガードレール①)は fail-closed のパラメータ化で実装**:
   検査式(param_count < data_count × k)は実装し、param_count / data_count / k は呼び出し側が供給。
   **k 未供給なら不合格**(安全側に倒す)。「パラメータ数の数え方」と k の値は U24 のまま
   (確定時は値を渡すだけ)。
2. **F-014-4(ガードレール④・候補)は機構のみ実装**:
   上限は呼び出し側供給。**未供給時は「未検査(U18 未確定)」を結果に明示し合否に含めない**
   (候補ガードのため探索を止めない)。供給時は超過で不合格。
   ①(必須ガード)と④(候補ガード)で未供給時の挙動を意図的に変えている点に注意。
3. **検査対象レコード(封印アクセスログ・選定来歴・開封トークン)の契約はテスト駆動で定義**:
   test-writer が API とともにレコード形式を定義し、実装・監査を経て確定後、
   `specs/GUARD_IF.md` として契約文書化する。後続の F-002(ログ生成)・F-012(来歴生成)・
   F-013(トークン利用)はこれに従う。

## 影響

- F-014 はブロッカー無しで全4ガードの実装に着手可能(①は値待ち、④は上限待ちの状態で完成)。
- U24/U18 の確定が遅れても探索・評価のフローを壊さない(①は安全側、④は明示スキップ)。
