# プロジェクト概要

- **一行サマリ**: baseline と独立に作る、同じ EPI 入出力契約を満たす新アーキ `supreme`。弱い5項目を「ルール改良＋少量学習の項目別混合」で底上げし、強い項目は baseline 実証ロジックを流用して守り、汚染ゼロの封印テストで baseline と同一土俵・項目別に勝敗を測る。
- **解決する問題**: 旧 supreme は20件のAI生成データに学習を盛りすぎ（最大ヘッド30k params ÷ 20件）、評価シナリオを学習に混入させて 0.828 を出した＝実力でなく丸暗記（部分メモライズ）。本プロジェクトは正しい手順（データ規律＋汚染ゼロ封印評価）で、baseline を**フェアに**超える。
- **スコープ内**: supreme アーキ本体 ／ データ増強・分割の規律 ／ 封印テスト構築 ／ 評価ハーネス ／ baseline 再計測。
- **スコープ外**: baseline 本体の改修（完成・凍結された基準）／ 旧 supreme の再現 ／ L1–L3 等の前段。
- **想定ユーザーと利用シーン**: 未確定（U14）。当面は研究者本人による実験運用と推定。

# アーキテクチャ

## 技術スタック
- 言語/FW/モデルロード機構: **未確定（U13）**。Python / PyTorch と推定するが本議論で明示合意なし。選定理由が確定するまで暫定値として扱う。
- 実行環境: 実験は GPU。最終デプロイは GPU/CPU いずれも可（D21）。
  - 選定理由: 誤差許容測定（D20）で機種差を吸収し、ガードレール①（学習軽量）で CPU でも回るため、デプロイ先を縛らない。
  - **GPU の要否**: 学習が必要になっても GPU は**常時必須ではない**。ガードレール①（param数 ≪ data数）により学習対象は小規模（数個〜数百, 旧最大でも30k）に限られ、CPU で現実的に学習可能。推論・封印評価は CPU で可。GPU が必須化するのは「少量学習」から外れて大モデルに振れた時のみで、それはガードレール上そもそも禁止方向。
  - **環境一致の論点（U23・要決定）**: 学習や評価を GPU で行うと CPU と数値が bit 一致しない。「GPUで学習→CPUで評価」のように環境を跨ぐと、GPU/CPU 差と T3 の真のドリフトが区別しにくくなり、再現性チェック（穴4・U5）が揺れる。**学習が要る項目は学習と評価の実行環境を揃えるか**を決める必要がある。

## システム構成
- **独立性**: supreme は baseline のコードに**実行時依存しない**自己完結実装。EPI 入出力契約のみ共有。baseline ロジックの「流用」は**設計参照／移植**を指し、実行時のリンクではない（独立性と両立、U9で形態を確定）。
- **項目構成**:
  - 強い項目（T0 / T1 / role / Anomaly）= baseline 実証ロジックを流用出発点とする。弱い項目モジュールとの相性は組み合わせ実験で判定。
  - 弱い5項目（mode / relation / T3 / Scene regime / Quality regime）= 改良モジュール。内部手法は U1（混合比）・U3（構造原因）確定後。
- **T3 状態**: 時系列状態を許容。条件 ①明示リセット可（RESET_T3 / EPISODE_SWITCH で必ず初期化）②再現性の定義＝「同じ入力**系列**＋同じリセット手順 → 同じ出力（誤差許容内）」。
- **外部依存**: GitHub 上の (a) baseline 結果（エラー分析用）(b) T3 コントラクト・シナリオ。SPEC からURLで参照する（下記「外部参照」）。

> **数値に関する重要注記**: 本書中の項目スコア（mode 0.51 / relation 0.34 / T3 0.61 / Scene 0.57 / Quality 0.64 / T0 0.84 / T1 0.91 / role 0.87）は、すべて**旧§5の汚染値（部分メモライズ条件）**である。真の baseline 値は封印再計測（F-013）まで不明。本書ではこれらを「弱い／強い」の**分類目的にのみ**用い、目標値としては用いない。supreme の目標は「再計測後の baseline 値」を項目別に上回ること。

# 機能要件

> 内部手法が U1/U3/U4 に依存する F-007〜F-011 は**枠のみ**を定義し、中身は未決定として明示する。実装者はこれらを勝手に解釈してはならない（特に F-008 の relation 配線漏れは**未検証の仮説**）。

## F-001: データ規律基盤
- 概要: シナリオ+GT を親シナリオ単位で管理し、練習用／封印が親系統を跨がぬよう分割。版・親子リネージを記録。
- アクター: 研究者、各データ機能（F-002/F-003/F-012/F-013）
- 入力: シナリオ+GT（`N04-scenario-contract.git` feat ブランチ @ `a0b8822`・catalog 1.4.0 の `scenarios/v021_core/`・20件・210フレーム・AI生成。ADR 0005 で改ピン）、増強で生成される派生シナリオ
- 出力: 親系統タグ付きデータセット、練習/封印の分割割当、GT 単一スキーマ（**実体は `specs/GT_SCHEMA.md`**・2026-06-12 実データから導出）
- 正常系: 各データに親系統IDを付与し、分割が親単位で交わらないことを保証して払い出す。**分割割当は datagov の自動割当**（封印件数/比率＋適格フィルタを受け、root 親系統IDの sha256 安定ソート順。乱数・時刻非依存の決定的アルゴリズム。ADR 0003）。
- 異常系: 分割が親系統を跨いだ場合は払い出しを拒否しエラー化。親系統不明データ・スキーマ違反データは登録拒否（拒否/警告の2段規則は GT_SCHEMA.md）。
- 境界条件: 増強で孫・ひ孫が出た場合、**リネージは推移的に親系統へ畳む**（孫経由リーク防止）。元シナリオ（人手作成含む）は**自身が root**（generation=0）。
- 対応コンポーネント: `datagov`
- 受け入れ条件:
  - F-001-1: 封印セットの全親系統IDが、練習用・増強の親系統IDリネージ集合と**交わらない**（集合演算で assert）。
  - F-001-2: GT は単一スキーマ（GT_SCHEMA.md）で表現され、baseline 結果GT（F-005）と封印GT（F-002）が同一フォーマットで突合可能。**検証は2段階**: F-001 時点は合成フィクスチャとの突合、F-002/F-005 実装時に実GTで再検証（ADR 0003）。
  - F-001-3: 任意データから親系統への遡及が推移閉包で一意に解決できる。
- 依存する他機能: なし（基盤）

## F-002: 封印テストセット構築
- 概要: 人手の本物シナリオ＋人確認GTを少数（精鋭）構築。学習・調整に不可触、最終評価で一度だけ開封。
- アクター: 研究者
- 入力: 人手作成シナリオ、人手確認GT
- 出力: 封印セット（アクセス制御下）
- 正常系: 本物シナリオを封印登録し、評価フェーズ以外からのアクセスを技術的に遮断。
- 異常系: 評価フェーズ外のアクセス試行を検出・記録・拒否。
- 境界条件: 件数は未確定（U2）。少数でも統計的扱い（U11）が要る。
- 対応コンポーネント: `sealset`
- 受け入れ条件:
  - F-002-1: 封印セットの各シナリオ親系統が F-001 のリネージで練習用と非交差。
  - F-002-2: 封印へのアクセスは**開封セッション単位で生涯1回のみ**。評価フェーズ＝guard（F-014）が発行する**開封トークンの有効期間**と機械的に定義し、有効トークン外の読み出しは拒否・記録する（セッションID付きアクセスログで検証、F-014）。
  - F-002-3: 封印GTは F-001 単一スキーマに準拠。
- 依存する他機能: F-001

> **注記（2026-07-02・ADR 0051）**: 実際の封印評価（2026-06-23/24）は本節の規定と異なり、AI 生成コーパス coverage_v1 の lineage-disjoint 分割で実施された。実際の封印データについては `decisions/0051-f002-seal-data-deviation-ratification.md` の逸脱記録（事後批准・将来の封印の規律）を参照。

## F-003: 練習用データ増強
- 概要: AI生成で練習用の量を確保。入力中心に増やし、GT は生成と別系統で確定。
- アクター: 研究者、AI生成器
- 入力: 元シナリオ（親）、生成パラメータ
- 出力: 増強練習用データ（親系統タグ付き）、別系統で確定したGT
- 正常系: 親から派生を生成し、親系統タグを付与して F-001 に登録。GTは生成と別ルートで確定。
- 異常系: GT が別系統で確定できない派生は破棄またはフラグ。
- 境界条件: 量は未確定（U2）。多様性の担保手段は未確定（U12）。
- 対応コンポーネント: `augment`
- 受け入れ条件:
  - F-003-1: 全増強データに親系統タグが付与され、推移閉包で親へ遡及可能。
  - F-003-2: 増強分GTは生成器と異なる手段で確定または検算されている（手段定義はU17）。
  - F-003-3: （多様性の定量条件は U12 確定まで受け入れ条件に含めない＝過剰約束を避ける）
- 依存する他機能: F-001
- 着手条件(2026-06-12 監査由来・ADR 0010 決定4): **(a) 封印後に train を追加する「逆方向交差」(統合ギャップG1)と、(b) 非rootレコード封印時に `sealed_lineage_set` が `parent_lineage_id` を未検算のまま信頼する検算素通り(欠陥D1)の両方について、検査統合点を設計に含めること**(`reports/audit-20260612-2238-F-002.md` の G1・D1。推奨案: sealset が governor へ meta 登録し datagov を単一リネージ権威にする)。

## F-004: 評価ハーネス（測定エンジン）
- 概要: 項目別スコアを誤差許容で測定する**再利用可能な測定エンジン**。T3 は系列再現チェックを含む。封印を1回開封して実行する運用は F-013 が担う（責務分離）。
- アクター: F-012（探索）、F-013（封印評価）
- 入力: supreme/baseline の出力、対象データセット、GT、指標定義、許容幅
- 出力: 項目別スコア、T3 再現判定
- 正常系: 指標式（U10）に従い項目別に採点。連続値は誤差許容、分類は完全一致で判定。
- 異常系: 指標定義・許容幅が未供給なら**実行せず停止**（適当な値を埋めない）。
- 境界条件: 指標単位（U10）が未確定の間はブロック。誤差許容は U5a/U5b で確定済み（環境一致＝U23 既定方針が前提）。
- 対応コンポーネント: `harness`
- 受け入れ条件:
  - F-004-1: 同一入力・同一指標定義で測定結果が決定的（ハーネス自体が乱数で揺れない）。
  - F-004-2: T3 は「同一入力系列＋同一リセット列を2回流し、連続値が `|a−b| ≤ ε_abs + ε_rel·max(|a|,|b|)`（ε_rel=1e-6, ε_abs=1e-9。U5a）以内・分類項目が完全一致」を判定できる。
  - F-004-3: 指標定義／許容幅が欠落した呼び出しはエラーで停止する。
- 依存する他機能: なし（エンジン）。U10（指標式）は ADR 0012 で確定済み＝**着手可能**（8層 micro acc・完全一致・NA分母除外・Anomaly採点外・risk_tier 210規約）。U5 は U5a/U5b として解決済み。

- 依存する他機能: U9（流用形態）。U7（契約）は解決済み（2026-06-12・ADR 0006）

## F-007: mode 改良モジュール

- 受け入れ条件: F-007-1: F-013 の封印評価で mode の項目別対比が測定・報告される（baseline 再計測値超えは合否ゲートでなく成功目標。「非機能要件・正しさ」参照）。
- 依存する他機能: F-005（構造原因）、ガードレール（F-014）

## F-013: 封印評価＋baseline 再計測
- 概要: 確定した組み合わせを封印で一度だけ評価。baseline も**同一封印**で再計測し、同じ土俵で項目別に対比。
- アクター: 研究者
- 入力: 確定組み合わせ（F-012）、封印セット（F-002）、ハーネス（F-004）、baseline
- 出力: 項目別の勝敗（弱い5項目↑ / 強い項目維持）
- 正常系: 封印を1回開封し、supreme と baseline を同一封印・同一指標で測定して対比。
- 異常系: ガードレール（F-014）が「封印が学習/調整に使用済み」を検出したら評価を中止。
- 境界条件: baseline は config 空の決定的パイプライン。封印シナリオを baseline に流すための**入力アダプタ（封印→PSO形式）**が必要。**baseline の実行自体は研究者が手動で実施する（システムの自動化対象外・2026-06-12 確定）**: sealeval は (1)アダプタで baseline 入力を生成 → (2)研究者が baseline を実行 → (3)出力を取り込み同一指標で採点する。指標式（U10）が前提（許容幅は U5a/U5b で確定済み）。
- 対応コンポーネント: `sealeval`
- 受け入れ条件:
  - F-013-1: supreme と baseline が同一封印・同一指標式で測定される。
  - F-013-2: 項目別対比（弱い5項目の勝敗・引き分け、強い項目の δ_strong 内維持判定）が同一封印・同一指標で測定され、報告される。差が δ_strong（U5b）以内は引き分けとして報告する。「弱い5項目↑ ∧ 強い項目維持」自体は合否ゲートでなく成功目標（「非機能要件・正しさ」参照）。
  - F-013-3: 封印開封が単一の**開封セッション**（guard 発行の開封トークン下）で行われ、本番封印の生涯開封セッション数が1（F-014 のセッションID付きログで検証）。supreme 測定と baseline 再計測の読込は同一セッション内なら「1回」と数える。

- 依存する他機能: F-002, F-004, F-012, F-014, **F-基盤-001（supreme end-to-end ランナー・実走に必須）**

- 依存する他機能: なし（横断的制御点）

# 非機能要件
- **正しさ／公平性**: 勝敗判定は**項目別**。強い項目を下げて弱い項目を上げる平均的ごまかしを禁止（却下: R6 平均判定）。
- **プロジェクト成功目標（合否ゲートでない・2026-06-12 再分類）**: 封印再計測で、弱い5項目それぞれ supreme > baseline、かつ強い項目の低下 ≤ δ_strong（U5b）。差が δ_strong 以内は引き分けとして報告する。少数封印での勝敗主張の統計的扱いは U11。

- **パフォーマンス（速度・スループット）**: 未議論（U該当なし→運用フェーズで定義）。

# 設計判断の記録

## 判断1: supreme を baseline と独立な新アーキにする
- 背景: 旧 supreme は baseline への config 差分（追加層）だった。baseline は別途ハーネスエンジニアリングで再開発・完成済み。
- 選択肢: (a) 凍結 baseline 上の追加層（全OFFで baseline 一致）／(b) baseline 独立の自己完結アーキ
- 選んだもの: (b)
- 理由: ユーザ方針。supreme は baseline を参考にしつつ独立に開発するもの。
- 却下した案の弱点: (a)=R2。supreme を baseline 実装に構造的に縛り、独立な設計探索を妨げる。
- リスクと見直しトリガー: 独立にしたことで強い項目を再発明し劣化させるリスク → F-006 流用＋項目別勝敗（D6）で抑制。劣化が止められなければ判断1を再検討。

## 判断2: 契約の固定点をアーキ／EPI契約に置き、数値・重みは契約外とする
- 背景: 旧挙動はドリフトして固定点でない（旧§5）。
- 選択肢: (a) 旧コードのbit再現／(b) アーキ・EPI契約を契約、数値は再生成対象
- 選んだもの: (b)
- 理由: 完全再現は不要・多少の性能低下可（Q2）。固定点でない挙動は再現できない。
- 却下した案の弱点: (a)=R10。再現対象が存在しない。
- リスクと見直しトリガー: 「何を再現するか」が緩むと検証の拠り所が消える → 拠り所を「封印での項目別勝敗」に固定。

## 判断3: 手段をルール×学習の項目別混合にする
- 背景: 弱い項目はルールが雑なだけのものと、学習が要るものが混在しうる。
- 選択肢: (a) ルール単独（supreme-rulebase）／(b) 学習主役／(c) 項目別混合
- 選んだもの: (c)
- 理由: 「上手に混ぜる」。項目ごとに最適手段が異なる。
- 却下した案の弱点: (a)=R4（学習が原理的に要る項目を取りこぼす）。(b) は20件で過学習。
- リスクと見直しトリガー: 「混ぜる」が「学習を盛る」に逆戻りする病 → ガードレール①②③で抑制。混合比はエラー分析後（U1）。

## 判断4: 過学習を3ガードレールで構造的に防ぐ
- 背景: 旧失敗の本質は param数30k÷data20＝丸暗記、かつ評価混入。
- 選択肢: (a) 封印テストのみ／(b) param制約＋封印不可触＋選定は練習用のみ
- 選んだもの: (b)
- 理由: 封印だけでは「組み合わせを引き直して当てる」過学習を防げない。
- 却下した案の弱点: 手調整=R5、引き直し最良採用=R7。いずれも別経路の暗記。
- リスクと見直しトリガー: 許容幅を緩めると再現性検査が形骸化 → U5 を最重要未決定に。

## 判断5: データは先に増強してから探索する／分割は親シナリオ単位
- 背景: 探索するなら封印を焼かずに済む練習用が要る。20件では train/test 分割が成立しない。
- 選択肢: (a) 先行増強→探索／(b) 組み合わせ事前決め打ち（増強後回し）
- 選んだもの: (a)
- 理由: 探索を行う前提なら増強は「後で」でなく前提。
- 却下した案の弱点: (b)=R8（探索の自由度を犠牲）。1件単位混在=R9（親子類似でリーク）。「増強は後で」=R12（探索する以上後回し不可）。
- リスクと見直しトリガー: 増強が「似たものの量産」になると練習用が痩せる → 多様性測定（U12）が要る。

## 判断6: 封印は人手の本物・少数精鋭、baseline も同一封印で再計測する
- 背景: AI作問にAI採点だと実力でなくAI同士の一致を測る循環になる。比較は同一物差しでないと成立しない。
- 選択肢: (a) 全AI生成のみで封印／(b) 人手の本物・少数＋baseline 同一封印再計測
- 選んだもの: (b)
- 理由: 封印は質最優先・量少なくてよい。比較の公平性は同一封印が必須。
- 却下した案の弱点: (a)=次善。親単位分割で凌げるが、AI作問にAI採点の循環リスクが残る。
- リスクと見直しトリガー: 本物封印で測ると baseline 値も今の数字から動く（下がりうる）→ これは初めて同一土俵に乗ることを意味し、目標値を「再計測後 baseline」に置換。少数ゆえ統計的有意性（U11）の扱いが要る。

# 用語集
- **EPI / PSO**: 出力レコード（EPI-T0..T3/CTRL/NOVEL。T3 の正式展開は Episodic Predictive Insight）／入力レコード（PSO-Snapshot/Delta。NS-EPI Input Contract）。**入力=PSO・出力=EPI** であり「EPI入力」という表現は用いない（2026-06-12 用語修正・ADR 0006）。
- **baseline / supreme**: 基準アーキ（完成・凍結）／本プロジェクトで作る新アーキ。
- **シナリオ+GT**: ラベル付きデータ（入力シナリオ＋正解 Ground Truth）。
- **封印テスト**: 学習・調整に一切触れない、最終1回だけ開封する評価用データ。
- **練習用データ**: 組み合わせ選定に使ってよいデータ。
- **親単位分割**: 増強の親シナリオ単位で練習/封印を分け、親系統を跨がせない（推移閉包で畳む）。
- **ガードレール①②③(④)**: param数≪data数 / 封印不可触 / 選定は練習用のみ /（候補）撤退基準。
- **弱い5項目 / 強い項目**: mode, relation, T3, Scene regime, Quality regime ／ T0, T1, role, Anomaly。
- **T0/T1/T2/T3**: 即時 / 動態 / 状況 / エピソードの4時間スケール（baseline 準拠）。
- **部分メモライズ**: 評価データを学習に混入させて見かけ上スコアを上げる汚染（旧 supreme の失敗）。
- **項目別勝敗**: 平均でなく項目ごとに、弱い5項目↑・強い項目維持を判定する成功基準（合否ゲートでなく成功目標。非機能要件参照）。
- **ε / δ_strong**: 再現性判定の誤差許容（U5a: ε_rel=1e-6, ε_abs=1e-9）／強い項目の低下許容幅（U5b: 絶対値 0.02・暫定）。
- **開封セッション／開封トークン**: 封印アクセスの計数単位と「評価フェーズ」の機械的定義。guard（F-014）が事前検査合格時にトークン（セッションID＋発行時刻）を発行し、F-013 終了で失効。有効期間内の読込全体を1開封セッション＝「1回」と数える。
- **「段階N」「旧§N」**: フェーズ1の構造化インタビュー資料（参考・契約外）の節参照。歴史的注記であり本書の契約内容ではない。
