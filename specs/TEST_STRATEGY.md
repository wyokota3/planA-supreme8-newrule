# テスト戦略 — NS-EPI L4 supreme（新アーキ）

> フェーズ1の成果物。`specs/TEST_STRATEGY.template.md` 準拠。SPEC.md / ARCHITECTURE.md と対で読む。
>
> **本プロジェクト固有の前提**: このシステムの失敗は「バグ」より「**方法論の汚染**（評価データのリーク・過学習・再現性喪失）」として現れる。よって通常のユニット/統合/E2E に加え、**方法論検証層（Methodology tests）**を第一級のテストレベルとして置く。旧 supreme は機能としては動いていたが、この層が無かったために 0.828 という偽の数字を出した。

# テストレベルと責務

- **ユニットテスト**: 各機能の純粋ロジック。リネージの推移閉包計算（F-001）、集合非交差判定、ハーネスの指標計算（F-004）、ガードレールの数値検査（F-014）、T3 のリセットで状態が初期値へ戻ること（F-009）。
- **統合テスト**: 機能境界。datagov→sealset/augment の分割が親系統を跨がない（F-001×F-002×F-003）、search が guard を必ず経由する（F-012×F-014）、sealeval が harness と baseline アダプタを正しく結ぶ（F-013×F-004）。
- **E2Eテスト**: UC-1（エラー分析→改良→探索）と UC-3（T3 系列再現）。**UC-2（封印評価）は E2E として常用しない**（封印は1回開封・後述の穴2）。代わりに**封印のダミー（合成データ）**で経路全体を通すドライランE2Eを置き、本番封印は最終1回のみ。
- **方法論検証層（本プロジェクトの中核）**:
  - リーク検査: 練習用と封印の親系統が非交差（F-001-1）。
  - 封印保全: 封印アクセスが評価フェーズ以外で0回（F-002-2 / F-014-2）。
  - 過学習ガード: 学習 param 総数 < 練習用データ数 × k（F-014-1）。
  - 選定純度: 組み合わせ選定が練習用スコアのみ（F-012-2 / F-014-3）。
  - 再現性: T3 が系列＋リセット手順単位で再現（F-004-2 / F-009-1）。
- **カバーしない領域とその理由**:
  - GT の正しさそのもの（後述の穴5）— テストの基準であって対象にできない。U17 のワークフローで担保する別問題。
  - 増強の多様性（U12）— 定量指標が未定義のためテスト化しない（過剰約束回避）。
  - L1–L3 等前段との統合（U20）— スコープ外。EPI 契約を境界とする。

# テストフレームワークとツール
- フレームワーク: **未確定（U13 依存）**。Python/PyTorch 推定なら pytest を暫定。確定まで本章は仮。
- アサーションライブラリ: 標準 assert ＋ 数値は許容誤差つき比較（ε は U5a で確定: `|a−b| ≤ 1e-9 + 1e-6·max(|a|,|b|)`。δ_strong=0.02 は U5b・暫定）。
- モック戦略: 封印セットは**合成ダミー封印**でモックし、経路を常用テストで流す。本番封印はモックしない（1回開封の対象）。baseline は再実行可能性が未確認（U22）のため、取込済み結果のフィクスチャでモック可能にする。
- テストデータ管理: 全テストデータに親系統タグ（F-001）。テスト用 fixture も練習/封印の区別を持ち、リーク検査テスト自身が fixture を跨がない。

# カバレッジ目標
- 行カバレッジ: 方法論検証層と F-001/F-004/F-014 は **高（目安90%+）**。これらが緩むと汚染を見逃す。
- 分岐カバレッジ: ガードレール（F-014）とリセット分岐（F-009）は分岐網羅必須。
- 100%を目指さない領域: 改良モジュール内部（F-007〜011）— 中身が U1/U3 未確定で、手法が決まるまでカバレッジ目標を置かない。

# テスト命名規約
- ファイル名: `test_<feature_id>_<観点>.py`（例: `test_F001_lineage_disjoint.py`）。
- テスト関数名: `test_<受け入れ条件ID>_<期待>`（例: `test_F001_1_seal_train_parents_disjoint`）。
- 表記注: 仕様IDは `F-001` だが、Python 識別子にハイフンが使えないためコード内では `F001` と表記する（意図的な揺れ）。
- 仕様IDとの対応付け: 各テストの docstring 冒頭に対応する受け入れ条件ID（F-XXX-N）を必須記載。auditor が「受け入れ条件 ↔ テスト」の網羅を機械照合できるようにする。

# 各機能要件のテスト方針

## F-001 データ規律基盤
- ユニット: リネージの推移閉包が孫・ひ孫まで親系統に畳まれる。GT単一スキーマのバリデーション。
- 統合: 分割払い出しが親系統を跨がない。跨いだ要求を拒否。
- 必須境界: 孫経由リーク（親A→子→孫を封印に、親Aの別の子を練習に）を**意図的に作って検出できる**こと。
- 必須異常系: 親系統不明データの登録拒否。

## F-002 封印テストセット
- 統合: 封印の各親系統が練習用と非交差（F-002-1）。
- 方法論: 評価フェーズ外アクセスの検出・拒否・記録（F-002-2）。
- 困難な部分と代替: 「1回だけ開封」は単発テストで繰り返し検証できない（穴2）→ **開封セッション数のカウンタ**（guard 発行トークンのセッションID付きログ）を対象にし、トークン発行・失効とカウンタの増加ロジックをテストする（封印本体は開けない）。

## F-003 練習用データ増強
- ユニット: 増強データに親系統タグが付与され親へ遡及可能（F-003-1）。
- 統合: 増強GTが生成器と別手段で検算されている（F-003-2、手段はU17）。
- カバーしない: 多様性（F-003-3 は受け入れ条件化していない・U12）。

## F-004 評価ハーネス（測定エンジン）【U10 依存・ブロッカー。U5 は U5a/U5b として解決済み】
- ユニット: 同一入力・同一指標定義で測定が決定的（F-004-1）。指標式（U10）が供給された時のみ採点、欠落時は停止（F-004-3）。
- 方法論: T3 の2回流し再現判定（F-004-2）— 連続値は `|a−b| ≤ 1e-9 + 1e-6·max(|a|,|b|)`（U5a）、分類は完全一致。
- 困難な部分: **指標式（U10）が未確定の間、採点結果のテストはブロック**（「停止することのテスト」は先行可）。ε は確定済みのため再現判定（F-004-2）のテストは書ける。

## F-005 baseline 取込＋エラー分析
- ユニット: baseline 結果GTと F-001 スキーマの突合。
- 統合: 弱い5項目の誤りが項目別・クラス別に出力（F-005-1）。
- 異常系: 想定外形式・再実行不能の報告（U22）。

## F-006 強い項目の流用移植【U7/U9 依存】
- 統合: supreme が baseline コードへ実行時リンクしていない（F-006-2、独立性の機械チェック）。
- 方法論: 弱い項目モジュールとの結合で強い項目が許容幅内に維持（F-006-1、許容幅は δ_strong＝U5b: 絶対値 0.02・暫定）。
- 困難な部分: 「下げない」は許容幅依存（穴7・累積劣化）。

## F-007〜F-011 改良モジュール【U1/U3（F-009 は U4 も）依存】
- 現時点のテスト方針: **枠のみ**。「封印で baseline（再計測値）を上回る」は合否ゲートでなく**成功目標**に再分類済み（2026-06-12）。各受け入れ条件は「F-013 で項目別対比が測定・報告されること」であり、方法論検証層（封印評価 F-013）で測る。内部ロジックのユニットテストは手法確定後。
- F-008 固有: **配線漏れ仮説をテストの前提に組み込まない**。F-005 の実エラー分析が出した原因に対してのみテストを書く。
- F-009 固有: リセットで状態が初期値へ戻る（F-009-2）。リセット発生源（U4）が未定のため、発生源を注入できるよう**リセットトリガを外部入力としてモック可能**に設計し、トリガ後の初期化をテスト。

## F-012 組み合わせ探索【U8 依存】
- 方法論: 探索中の封印アクセス0回（F-012-1）、選定が練習用スコアのみ（F-012-2）、試行回数が上限内（F-012-3、上限は U18）。
- 困難な部分: 探索空間（U8）未定のため探索ロジック本体のテストはブロック。封印非アクセスの検査は U8 と独立に先行実装可。

## F-013 封印評価＋baseline 再計測【U5/U10/U6 依存】
- 統合: supreme と baseline が同一封印・同一指標式で測定（F-013-1）。封印→PSOアダプタの整合。
- 方法論: 封印開封＝単一の開封セッション（F-013-3。開封トークンは F-014 が発行）。F-013-2 は項目別対比（勝敗・引き分け＝δ_strong 内差）の測定・報告。「弱い5項目↑ ∧ 強い項目維持」は成功目標であり合否ゲートでない。
- 困難な部分: 本番封印で1回しか実行できない（穴2）→ ダミー封印で経路を常用テスト、勝敗ロジックはダミーで検証、本番は最終1回。統計的有意性（U11）は本テストの**外**（穴1）。

## F-014 ガードレール検証（制御点）
- ユニット: param総数 < data数×k（F-014-1）、封印アクセス検査（F-014-2）、練習用のみ選定の検査（F-014-3）、試行上限（F-014-4・候補）。
- 統合: 違反検出時に後続（探索・封印評価）を**実際にブロック**する。
- 必須: ガードレールが「合格を出すべきでないケースで合格を出さない」陰性テスト（過学習構成・リーク構成・封印多重アクセス構成を**わざと作って**ブロックされること）。

# 非機能テスト
- パフォーマンステスト: 未議論。CPU/GPU 双方で動くこと（移植性）の smoke のみ暫定。
- セキュリティテスト: 音環境データの扱い未議論。封印アクセス制御は方法論検証層でカバー。
- 負荷テスト: 対象外（研究運用想定・U14）。
- 再現性テスト（非機能の中核）: 同一入力系列＋同一リセット手順で出力が誤差許容内に再現。GPU 非決定性と T3 ドリフトを ε で切り分ける（穴4）。

# テストの実行と維持
- ローカル実行手順: 方法論検証層 → ユニット → 統合 → ドライランE2E の順。**本番封印評価は手動・1回限りの別コマンド**（CI に含めない）。
- CI実行方針: 方法論検証層を必須ゲートにする（リーク・封印保全・過学習ガード・選定純度・再現性）。これらが落ちたら機能テストの合否に関わらずビルド失敗。
- フレーキーテスト対処: GPU 由来の数値揺れは ε（U5a）で吸収。ε で吸収すべきでない T3 ドリフトと区別がつかなくなったら、それは ε 設定の誤りとして扱う（穴4）。
- テスト破損時の優先度判断: 方法論検証層 > 機能テスト。汚染を見逃すテストの破損を最優先で直す。

# このテスト戦略の穴（8個）

> 2026-06-12 注記: U5 は U5a（ε 確定）/U5b（δ_strong 暫定 0.02）として解決、F-007-1〜F-011-1・F-013-2 の「上回る」は成功目標に再分類済み。以下の「穴」と次章「捕捉できない条件」は**限界の記録**として原文を保持する（穴4「ε の妥当性自体は検証不能」は値が確定した今も本質的に残る。穴6 の k は U24 へ採番済み）。

1. **統計的検出力が無い**。練習用を増やしても封印は少数（D16）。封印で「supreme > baseline」が出ても、差が実力か偶然かを区別する検定枠組みが無い（U11）。本戦略は点推定の比較に留まり、「勝った」の主張に信頼区間を与えられない。→ 捕捉不能: **F-013-2 の勝敗判定**は統計的有意性を含まない。

2. **封印評価は回帰テストにできない**。封印は1回開封（D12）。通常テストは何度でも流せる前提だが、封印評価は流すたびに封印が焼ける。よって「baseline を超えた」を保証する最重要テストが、CI で継続監視できない。コード変更のたびに再評価できず、回帰を封印で検出できない。→ ダミー封印で経路は守れるが、**本番の勝敗そのものの回帰は守れない**。

3. **リーク検査はリネージ記録の正しさに依存**。F-001-1 の非交差判定は「親系統タグが正しい」前提。タグ付け（F-001/F-003）自体が間違っていたら、リーク検査は通っても実際はリークしている。**リネージの正しさを保証するテストが、リネージを使うテストと独立でない**（自己参照）。→ 外部の真値（人手確認した親子対応）でリネージを抜き取り検査する以外に手が無いが、それは未定義（U17 隣接）。

4. **ε のキャリブレーションがテストできない**。再現性テストの許容 ε（U5）は、緩すぎれば T3 ドリフトを「再現OK」と誤判定し、厳しすぎれば GPU 機種差で偽陽性。**ε が正しいことを検証する上位テストが無い**。εは人が決めた定数で、その妥当性はテスト対象外。→ 旧 supreme の「再走で drift」を二度と起こさないための核心なのに、ここが定数頼み。

5. **GT の正しさはテストの外**。全テストが GT を正解として使う。GT が（特に AI 生成分が）間違っていれば、全テストが誤った基準で「合格」する。封印は人手GT（D16）で緩和されるが、練習用・増強分は AI 系。**テストの土台が GT であり、GT 自体は本戦略で検証できない**（U17）。→ 捕捉不能: GT 依存の全受け入れ条件（実質ほぼ全部）。

6. **ガードレール①の係数 k が恣意的**。F-014-1 の「param < data×k」は k 次第で過学習判定が変わる。k の根拠（なぜ 0.1 か 1 か 10 か）が無く、**k の正しさを検証するテストが無い**。ガードレールが形式的に通っても、k が甘ければ過学習を許す。

7. **強い項目の累積劣化を単発テストが捉えない**。F-006-1 は「許容幅内」を各時点で見るが、複数の弱い項目改良が**それぞれ許容幅内で少しずつ**強い項目を削ると、合計で大きく劣化しうる。単発の許容判定では累積を検出できない。→ ベースライン固定の累積リグレッション監視が要るが未設計。

8. **封印非アクセスの保証がログ経由に限られる**。F-012-1 / F-014-2 はアクセスログで封印の不使用を検査する。だがログを介さない経路（ファイル直読み、別プロセス、手作業でのコピー）があれば検査をすり抜ける。**「ログに出ないアクセス」を検出できない**。技術ロック（権限・暗号化）まで踏み込まないと保証にならないが、そこは未設計。

# この戦略で捕捉できない SPEC 受け入れ条件（明示）

- **F-013-2（弱い5項目で supreme > baseline ∧ 強い項目維持）**: 勝敗は測れるが、その差の**統計的有意性は捕捉外**（穴1）。少数封印での「勝った」は点推定。
- **F-003-3（多様性）**: そもそも受け入れ条件化していない（U12）。テストも無い。「似たものが増えただけ」を検出できない。
- **F-001-1（練習/封印の親系統非交差）**: 判定は書けるが、**リネージ記録が正しい前提**であり、記録の正しさは捕捉外（穴3）。
- **F-004-2 / F-009-1（T3 再現）**: 再現の判定は書けるが、**判定に使う ε の妥当性は捕捉外**（穴4）。
- **GT を正解とする全条件**（F-007-1〜F-011-1 ほか）: GT の正しさが捕捉外（穴5）。封印の人手GTで部分的に緩和されるのみ。
- **F-014-1（過学習ガード）**: 検査は書けるが、**閾値 k の妥当性は捕捉外**（穴6）。

> 総括: 機能の正しさは通常テストで守れる。守りきれないのは「**方法論が正しいことの最終保証**」——統計的有意性・GTの真正性・εとkの妥当性・封印の物理的保全。これらは*テストで閉じない*ので、SPEC 未決定（U5/U10/U11/U17/U18）の確定と、人手レビュー・外部真値による抜き取りで補う前提とする。テストはこれらが「未確定なら停止する／違反なら止める」ことだけを機械的に保証する。
